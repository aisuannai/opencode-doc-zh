权限

权限（Permissions）控制智能体能否对某个资源执行某个动作。核心是一条条「动作 + 资源 + 效果」的规则，按顺序匹配、最后一条匹配的规则胜出。

配置（Configure）

一个常见的配置是：运行 shell 命令前先询问，放行常规的 Git 只读检查，永远禁止推送。把下面这组有序规则加进 opencode.jsonc：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" },
  ],
}

最后一条匹配的规则胜出，所以具体的例外要放在宽泛规则的后面。

⚠️ 注意

V1 使用不同的字段名和动作名。V2 请用 permissions、shell、subagent，而不是 V1 的 permission、bash、task。

规则（Rules）

每条规则需要三个字符串字段：

字段含义
action工具权限动作
resource被使用的值，如路径、命令、URL、查询词、skill ID 或智能体 ID
effectallow、deny 或 ask
jsonc
{
  "permissions": [
    { "action": "read", "resource": "*", "effect": "allow" },
    { "action": "read", "resource": "*.env", "effect": "deny" },
  ],
}
效果结果
allow直接放行，不提示
deny阻止该操作
ask等待客户端做出决定

没有任何规则匹配时，OpenCode 使用 ask。

匹配规则（Matching）

动作和资源使用简单的整值通配符：

模式匹配
*零个或多个字符，包括 /
?恰好一个字符
其它字面字符
jsonc
{
  "permissions": [
    { "action": "edit", "resource": "packages/docs/*.mdx", "effect": "allow" },
  ],
}

这个模式匹配整条规范化（normalized）后的路径。反斜杠会被规范化为正斜杠，Windows 上匹配不区分大小写。

以 * 结尾的 shell 模式还匹配不带参数的命令：

jsonc
{ "action": "shell", "resource": "git status *", "effect": "allow" }

它同时匹配 git status 和 git status --short。

OpenCode 按顺序组合规则并采用最后一条匹配项。加载顺序是：先加载低优先级配置，然后追加全局规则，最后追加智能体规则。

jsonc
{
  "permissions": [
    { "action": "read", "resource": "*", "effect": "allow" },
    { "action": "read", "resource": "secrets/*", "effect": "deny" },
  ],
}

一个操作可能同时检查多个资源，比如一个补丁涉及多个文件。任意一个 deny 就否决整个操作；否则任意一个 ask 就询问；否则操作被放行。

动作一览（Actions）

V2 的动作名是普通字符串，所以插件可以定义更多动作。内置工具目前使用这些动作和资源：

动作资源
read相对位置（Location）的内部路径，或规范化的外部绝对路径
editedit、write、patch 的目标路径
glob请求的 glob 模式
grep请求的正则表达式（不是搜索路径）
shell扫描器产出的命令字符串；复合命令可能产出多条
subagent目标智能体 ID
skillSkill ID
question*
webfetch请求的 URL
websearch搜索查询词
experimental_image_generate选定的图像模型，形如 providerID/modelID，设置了变体时再加 #variant
external_directory规范化的外部目录边界，通常以 /* 结尾
<server>_<tool>MCP 工具为 *；两个名称中不支持的字符都变成 _
opencode_list_mcp_resourcesMCP 服务器名称
opencode_read_mcp_resource<server>:<uri>
execute*；设为 deny 会移除 Code Mode 并改为直接列出其工具，嵌套工具各自执行自己的规则

例如，只允许一个 skill、禁止其它所有 skill：

jsonc
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "deny" },
    { "action": "skill", "resource": "effect", "effect": "allow" },
  ],
}

💡 扩展

doom_loop 和 lsp 不是当前 V2 核心的权限动作——旧文档里见过的话，那是过时的名称。

目录（Directories）

既不在当前活动位置（Location）之内、也不在其非根项目 worktree 之内的路径，会先按 external_directory 检查，再检查它的 read / edit 规则。默认策略允许 external_directory，所以外部路径默认不会触发提示，除非你自己加规则。想在任何项目外访问前先询问：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "external_directory", "resource": "*", "effect": "ask" },
  ],
}

在它之后放更窄的规则，可以对特定目录放行或禁止：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "external_directory", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "read", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "edit", "resource": "~/projects/reference/*", "effect": "deny" },
  ],
}

这适用于 read、edit、write 和 patch 用到的外部路径。shell 在检查 shell 资源之前，会先检查它的外部工作目录和扫描器推断出的目录。

对 external_directory、read 和 edit，开头是 ~、~/、$HOME 或 $HOME/ 的路径会在配置加载时被展开：

jsonc
{ "action": "read", "resource": "$HOME/reference/*", "effect": "allow" }

shell 资源保持原始命令文本，不做主目录展开。

⚠️ 注意

shell 以宿主机用户的完整文件系统、进程和网络权限运行。从命令文本推断目录只是尽力而为，所以与其写一堆想识别「所有危险命令」的模式，不如直接维护一个窄的 shell 白名单。

相对路径的修改类操作可能离开活动位置但仍在项目 worktree 之内。显式的外部路径在匹配前会先规范化，所以只对可信的目录边界做授权。

Shell 扫描器（Scanner）

shell 权限检查使用 OpenCode 内置的 shell 扫描器，覆盖 Bash、Zsh、POSIX sh 和 PowerShell。当命令语法畸形或包含扫描器无法安全分析的动态求值时，会返回一个扫描器错误，而不是执行未经校验的子命令：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "policies": [
    {
      "permissions": [
        { "action": "shell", "resource": "git status *", "effect": "allow" },
        { "action": "shell", "resource": "rm *", "effect": "deny" },
      ],
    },
  ],
}

权限规则、保存过的批准模式和尽力而为的目录推断，适用于每个提取出的子命令和 cd 目标。对未知目录没有额外的批准模式，也没有一刀切的限制。

默认策略（Defaults）

每个智能体（包括自定义智能体）都从这个有序的基础策略开始：

jsonc基础策略
[
  { "action": "*", "resource": "*", "effect": "allow" },
  { "action": "read", "resource": "*.env", "effect": "ask" },
  { "action": "read", "resource": "*.env.*", "effect": "ask" },
  { "action": "read", "resource": "*.env.example", "effect": "allow" },
]

随附的智能体会在其上追加这些策略：

智能体追加的策略
build允许提问（questions）
plan允许提问；除 ~/.opencode/plan 下的文件外禁止编辑
general禁止提问和启动子智能体
explore除 shell、读取、glob、grep、网页抓取、网页搜索和外部目录外全部禁止；读取 .env 时询问
title禁止所有动作
summary禁止所有动作
compaction保持基础策略

因为默认没有规则对 external_directory 设为 ask，所以位置和 worktree 之外的读写会不做提示直接进行。想恢复提示或阻止外部访问，按「目录」一节所示加一条 external_directory 的 ask 或 deny 规则。靠后的全局规则和智能体规则会覆盖这些默认值。

智能体专属权限（Agents）

共享规则放在顶层，更窄的规则放在 agents.<id>.permissions 下：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
  ],
  "agents": {
    "reviewer": {
      "description": "Review code without changing it",
      "mode": "subagent",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" },
      ],
    },
  },
}

智能体规则是追加在全局规则之后的，不会替换全局数组。自定义子智能体使用自己的权限，而不是父智能体权限的子集。

批准（Approvals）

当一条规则解析为 ask 时，客户端可以用以下方式回复：

选择回复结果
仅允许一次once只批准当前这一条待定请求
总是允许always批准它，并把工具建议的模式保存到项目中
拒绝reject拒绝它，以及该会话中所有其它待定的权限请求

例如，对 git status --short 选择「总是允许」，可能会保存一条覆盖后续 git status 命令的 shell 前缀：

text保存的模式
shell: git status * → allow

保存的批准是持久的、项目范围的 allow 规则。它们永远不会覆盖配置好的 deny。保存的模式由工具自己提议：有的工具提议 *，shell 提议命令前缀，skill 和子智能体提议各自的 ID。请定期检查宽泛的批准并删掉不再需要的。

客户端可以在拒绝时附加反馈。非交互式客户端必须自己决定如何处理批准请求；配置好的 deny 规则始终强制生效。

策略（Policies）

策略（Policy）可以在上述规则和保存的批准都跑完之后，对一次权限检查做硬性拒绝。它把 allow 或 ask 变成 deny，永远不会授予访问：

jsonc
{
  "policies": [{ "action": "tool.use", "resource": "shell:sudo *", "effect": "deny" }],
}

🧠 通俗理解

权限是「你自己给家里定的规矩」，策略是「物业/公司强制执行的规定」。哪怕你的项目配置里写了 allow，组织和 Console 下发的策略仍能把它硬生生压成 deny——全局策略和 Console 管理的策略覆盖项目配置，组织就是这样拦住某个仓库本身想放行的命令的。这是企业落地的最后一道闸。
