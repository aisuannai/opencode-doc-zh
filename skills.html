Skills

Skill（技能）是一份可以反复使用的任务说明书：写一个 SKILL.md 放进 .opencode/skills/<skill-id>，在 description 里写清楚什么时候用，智能体就会在合适的时机自己加载它。

.opencode/skills/git-release/SKILL.mdMarkdown
---
name: Git Release
description: Prepare release notes, version bumps, and GitHub releases
---

## Workflow

1. Read `references/release-policy.md`.
2. Summarize merged changes since the previous tag.
3. Propose the version bump before changing files.
4. Run `scripts/changelog.ts` only after the user approves the version.

当这个 skill 相关时，OpenCode 会把它「广告」给模型。智能体随后可以用 skill 工具加载它的指令内容——而不是把每个 skill 的全文都塞进每一条 prompt。

🧠 通俗理解

Skill 就像公司的标准作业流程（SOP）手册：平时放在柜子里，只在封面写一句「适用场景」。员工（模型）干到相关任务时，翻开对应那本，按步骤执行。这比把所有手册内容都印在员工入职培训里（每条 prompt 全塞进去）要省得多、也精准得多。

创建

把相关的脚本、参考文档和模板和 SKILL.md 放在一起：

text目录结构
.opencode/skills/
└── git-release/
    ├── SKILL.md
    ├── scripts/
    │   └── changelog.ts
    └── references/
        └── release-policy.md

skill 里写的路径相对于包含 SKILL.md 的目录。推荐使用这种目录形式，因为它给配套文件一个私有的基准目录。

发现机制

OpenCode 会自动搜索这些位置：

范围来源
全局~/.config/opencode/skills
全局兼容目录~/.claude/skills、~/.agents/skills
项目.opencode/skills
项目兼容目录.claude/skills、.agents/skills

对项目来源，OpenCode 从当前目录逐级向上搜索到项目根，每一级的匹配目录都会纳入。

每个来源里可以放两种形式：

text单文件或目录
skills/
├── review.md
└── git-release/
    └── SKILL.md
  • Markdown 文件必须位于来源根目录，如 skills/review.md。
  • 文件名恰好是 SKILL.md 的文件可以嵌套在分组目录里，如 skills/git-release/SKILL.md 或 skills/teams/release/SKILL.md。
  • 一个包含 SKILL.md 的目录算一个 skill。OpenCode 不会在它内部继续找更多 skill。
  • 隐藏文件、隐藏目录和 node_modules 会被跳过。
  • 搜索最多深入到来源根目录以下六层目录。

来源（Sources）

在任意 opencode.json 或 opencode.jsonc 里用 skills 数组添加更多本地目录或 HTTP 目录（catalog）：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "skills": [
    "./team-skills",
    "~/shared/opencode-skills",
    "/opt/company-skills",
    "https://example.com/opencode/skills/",
  ],
}
值解析方式
相对路径相对OpenCode 当前的工作目录，而不是配置文件所在目录
~/ 路径相对当前用户的主目录
绝对路径按原样使用
http:// 或 https:// URL作为 HTTP 目录（catalog）加载

每一个被发现的配置文件都会贡献自己的条目；多个 skills 数组是合并关系，不是替换。

已连接的 OpenCode Console 工作区也可以共享 skill。

HTTP 目录（Catalogs）

一个 HTTP catalog 就是一个基础 URL 加一个 index.json：

index.jsonJSON
{
  "skills": [
    {
      "name": "git-release",
      "version": "3",
      "files": ["git-release.md", "references/release-policy.md"]
    }
  ]
}

对于这个条目，OpenCode 会从 <base-url>/git-release/<file> 下载每个文件。

规则要求
路径必须安全、相对、且与 index 同源（same-origin）
条目文件必须包含 SKILL.md 或 <name>.md，如 git-release.md
更新文件变化时递增 version，OpenCode 才会刷新缓存

每个下载下来的 skill 目录都会成为一个以条目命名的来源根目录，所以 git-release.md 和 SKILL.md 的 ID 都是 git-release。

Frontmatter

用 frontmatter 给 skill 命名并控制它的出现方式：

SKILL.mdMarkdown
---
name: Git Release
description: Prepare a repository release
metadata:
  opencode/autoinvoke: false
---

Prepare the changelog, version bump, tag, and release notes.
字段行为
name显示名；默认取自路径推导出的 ID
description展示给模型的摘要，用于判断何时使用
metadata.opencode/autoinvoke设为 false 可以把 skill 从模型可用列表中移除
disable-model-invocation设为 true，效果同 opencode/autoinvoke: false

运行时所有 frontmatter 都是可选的。希望模型能发现这个 skill 时，一定要写清楚 description；没有 description 的 skill 不会被「广告」出去。

⚠️ 注意

opencode/autoinvoke: false 只是把 skill 从模型的可用列表里隐藏，skill 仍然处于注册状态，仍可以被显式按 ID 加载。同时设置 disable-model-invocation 和 opencode/autoinvoke 时，opencode/autoinvoke 优先。V2 接受 license、compatibility 等可移植性字段，但不会解释它们。

ID 规则

skill ID 由文件路径决定，frontmatter 里的 name 只是个显示标签。

文件ID
<source>/git-release.mdgit-release
<source>/git-release/SKILL.mdgit-release
<source>/teams/release/SKILL.mdrelease

ID 是精确匹配且区分大小写的。想要 skill 可移植，建议用 1–64 个字符、全小写 kebab-case 的唯一 ID，并与目录名保持一致：

text推荐的正则
^[a-z0-9]+(-[a-z0-9]+)*$

V2 目前不强制这个正则、1–64 字符建议、name 与目录名一致，也不限制 description 长度。

优先级（Precedence）

skill 按 ID 选取。如果两个来源都定义了 git-release，后注册的来源提供的 skill 会被 OpenCode 加载：

text低优先级 ← 高优先级
~/.config/opencode/skills/git-release/SKILL.md  ← lower precedence
.opencode/skills/git-release/SKILL.md           ← loaded

来源按从低到高的优先级注册：

  1. 内置 skill
  2. .claude/skills，全局优先，然后从最远的祖先目录向当前目录
  3. .agents/skills，全局优先，然后从最远的祖先目录向当前目录
  4. ~/.config/opencode/skills
  5. 项目的 .opencode/skills，从项目根向当前目录
  6. 显式 skills 配置条目，按配置优先级和数组顺序

⚠️ 注意

除非你确实想覆盖先前的 skill，否则不要制造重复 ID——重名不会报错，而是悄悄替换，排查起来很麻烦。

加载过程

在每一步模型调用时，OpenCode 会列出所有有 description 且没有把 opencode/autoinvoke 设为 false 的已许可 skill。列表只包含 ID、名称和 description，不包含 Markdown 正文。

模型用精确 ID 调用 skill 工具来加载一个 skill：

skill tool inputJSON
{
  "id": "git-release"
}

OpenCode 随后：

  1. 选出该 ID 当前的定义。
  2. 检查所选智能体的 skill 权限。
  3. 把 Markdown 正文（不含 frontmatter）加入对话。
  4. 提供 skill 的基准目录，以及最多十个配套文件的路径样本。

想自己手动加载，在 prompt 里提到 @skill-id 即可。

💡 扩展

配套文件的内容不会自动加载——智能体会按 skill 正文的指示去读它们。文件路径样本只有目录式（含 SKILL.md）的 skill 才有；扁平的单文件 Markdown skill 不会收到相邻文件列表。所以复杂 skill 优先用目录形式。

权限（Permissions）

用 skill 动作、skill ID 作为资源。规则按顺序运行，最后一条匹配的规则胜出：

opencode.jsoncJSONC
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "allow" },
    { "action": "skill", "resource": "internal-*", "effect": "deny" },
    { "action": "skill", "resource": "experimental-*", "effect": "ask" },
  ],
}
效果行为
allow广告展示并加载匹配的 skill，无需批准
ask广告展示匹配的 skill，加载前先询问
deny对模型隐藏匹配的 skill，并拒绝加载

把同样的规则放到 agents.<id>.permissions 下，可以让它们只作用于某个智能体。

排查问题（Troubleshooting）

比如下面这个 skill 的 ID 是 release，而不是 frontmatter 里的名字 Git Release：

text路径 → ID
.opencode/skills/release/SKILL.md
                      └─ ID: release

如果某个 skill 找不到，或者加载了错误的内容，按以下步骤排查：

  1. 确认文件要么是根级的 *.md，要么是嵌套的、文件名恰好为 SKILL.md 的文件。
  2. 检查路径推导出的、区分大小写的 ID，而不是 frontmatter 的 name。
  3. 如果希望模型发现它，加上 description。
  4. 检查 opencode/autoinvoke 设置和所选智能体的 skill 权限。
  5. 看看是否有后注册的来源定义了相同 ID。
  6. 对于 HTTP catalog，检查 index.json、同源文件路径，以及 version 是否已更新。
