API 概览

Console API 让你的脚本和集成程序可以直接调用模型。每个请求都用 API key 完成认证。

bash列出可用模型
curl --fail-with-body "https://opencode.ai/inference/v1/models" \
  --header "Authorization: Bearer oc_sk_..."
API端点
Models（模型）https://opencode.ai/console/api/v1/models
Inference（推理）https://opencode.ai/inference/...
Providers（提供商）https://opencode.ai/inference/custom/...

🧠 通俗理解

把 Console API 想成「给机器用的 Console 网页版」：你在网页上能做的事（看模型、发推理请求、管预算），脚本也能通过 API 做。三个入口各有分工——Models 负责列出你有哪些模型可用；Inference 负责真正调用模型、拿到回复；Providers 负责接你自己的自定义提供商。而打开这扇门的钥匙就是 API key（形如 oc_sk_... 的密钥）。

API keys

工作区成员（workspace member）和服务账号（service account）都可以持有 API key。调用时把 key 作为 bearer token 放进请求头：

text
Authorization: Bearer oc_sk_...
个人 API key（Personal API key）服务账号 key（Service account key）
由谁创建任意成员，为自己创建Owner 和管理员（admin）
在哪里创建Account › Personal API keysSettings › Service accounts
以谁的身份行事创建它的那个成员对应的服务账号
用量计入谁的该成员的预算（budget）该服务账号的预算
适合场景你自己的脚本和 HarnessesCI、共享机器、集成程序
  • 每个 key 只属于一个工作区，在创建时选定，请求时无需再带工作区 header。
  • 完整 key 只在创建后的那一刻显示一次，之后 Console 里只能看到它的前缀。
  • 过期时间（Expiration）可选：Never（永不过期）、1 天、7 天、30 天，或自定义（Custom，1 到 365 天）。过期的 key 无法续期，只能新建一个。

⚠️ 注意

完整 key 只显示一次——弹出来的那一刻就要复制保存好（建议放进密码管理器或 CI 的密钥变量里），关掉弹窗后就再也找不回来了，只能删掉重建。另外，过期的 key 不能「续命」，必须新建并替换掉所有用到它的地方。

个人 API keys

个人 key 以你本人的身份行事。你的角色（role）、预算和模型规则都会自动作用到它身上。

  1. 从账号菜单打开 Account，找到 Personal API keys。
  2. 点击 Add API key。
  3. 选择工作区（Workspace）、填写 Key name，可选填过期时间（Expiration）。Owner 和管理员还能选择权限（Permissions）。
  4. 点击 Create，复制生成的 key。
textkey 的样例格式
oc_sk_1a2b3c4d5e6f_...

这个 key 跟随你当前对该工作区的访问权限：你的角色变了，key 能做的事也跟着变。如果工作区启用了 SSO 强制登录，那么除非你是 owner，否则这个 key 只在你有活跃 SSO 会话时才能使用。

服务账号

服务账号（service account）是工作区里的「非人类成员」，拥有自己的 API key、用量和预算。把自动化任务挂在它名下，用量就不会算到某个具体的人头上。它由 Owner 和管理员管理。

  1. 打开 Settings › Service accounts，点击 Add Service Account，起个名字，例如 CI Pipeline。
  2. 进入这个服务账号，点击 Add API Key。
  3. 填写 Key name、可选的过期时间（Expiration）和权限（Permissions），然后点击 Create。
  4. 复制 key。
bash把 key 存进环境变量
export SERVICE_API_KEY="oc_sk_..."

Owner 和管理员之后还能通过 key 操作菜单里的 Edit… 重命名服务账号的 key，或修改它的权限。

权限

每个 key 都有一个权限级别，在创建时的 Permissions 下选择：

权限级别允许做什么
All（全部）该成员或服务账号能做的一切，唯独不包括 This account's API keys。
Restricted（受限）只做你勾选的资源相关的事。
Read only（只读）对所有资源只读。可以列出模型，但不能调用它们。

🧠 通俗理解

权限的「天花板」原则：key 永远不能比它的主人更能干。个人 key 的上限是你当前的角色权限，服务账号 key 的上限是服务账号本身能做的事。所以如果你只是个普通成员，就算想给 key 开「全部权限」也开不出来——这保证了不会有人绕过角色体系拿到额外的能力。

受限 key（Restricted keys）

选了 Restricted 之后，可以为每类资源分别设置 None（无）、Read（读） 或 Write（写）。Write 包含 Read 的能力。

资源可选级别
Models（模型）Read、Request
Usage（用量）Read
Budgets（预算）Read、Write
Members（成员）Read、Write
Providers（提供商）Read、Write
Billing（账单）Read、Write
Workspace settings（工作区设置）Read、Write
SSORead
Service accounts（服务账号）Read
This account's API keys（本账号的 API key）Write

Models › Read 只能列出模型；Models › Request 则额外允许通过 Inference 和 Providers API 真正调用模型。举例：一个只用来调用模型的 key，这样配置就够了：

text
Permissions: Restricted
Models:      Request

在引入细分权限之前创建的 Inference only key，现在会显示为 Restricted，且 Models 已设为 Request。

谁能授予什么

  • 普通成员只能创建「列出并调用模型」的个人 key。Console 不会给他们权限选项，而是直接显示一句提示：「This key can list and call models as you.」（此 key 可以以你的身份列出并调用模型。）
  • Owner 和管理员可以给自己的个人 key 选 All、Restricted 或 Read only，上限是自己角色的能力。默认值是 Restricted 且 Models 设为 Request。如果他们之后被降级，他们的 key 的权限也会随之收缩。
  • 服务账号 key默认为 All，由 Owner 和管理员来设定权限。

限制（Limitations）

有些操作永远需要真人登录 Console，用 key 创建 key 的行为也被严格限制：

  • 任何 API key 都不能修改 SSO 设置，也不能删除工作区。
  • 服务账号 key 不能邀请成员、更改角色、移除成员、管理账单、修改工作区设置、管理模型，也不能创建或删除服务账号——即使持有 All 权限也一样。
  • This account's API keys 只出现在服务账号 key 上，而且 All 并不包含它。持有它的 key 只能为它自己所属的服务账号创建和吊销 key。新建的 key 必须是 Restricted、不能超出创建它的 key 的权限范围，也不能再带上 This account's API keys。
  • 个人 key 永远拿不到 This account's API keys，并且任何 API key 都不能创建或吊销个人 API key。

⚠️ 注意

超出 key 权限范围的请求会返回 HTTP 403（禁止访问）。如果你的脚本突然集体报 403，先检查是不是 key 的权限被改过、key 的主人被降级过，或者 key 已经过期/被吊销（那种情况通常返回 401）。

吊销（Revocation）

Key 类型谁能吊销在哪里操作
个人 API key持有它的成员本人Account › Personal API keys，然后 Revoke
个人 API keyOwner 和管理员Settings › Members 中该成员的页面，API Keys 一栏
服务账号 keyOwner 和管理员Settings › Service accounts 中该服务账号的页面，API Keys 一栏

除了手动吊销，key 还会被自动吊销：

  • 离开或被移出工作区，或通过 SCIM 被取消配置（deprovision），会吊销这个人在该工作区创建的所有 key，包括其创建的服务账号 key。同一服务账号上由其他人创建的 key 不受影响，继续可用。
  • 删除一个服务账号会吊销它的全部 key。

💡 扩展

被吊销和已过期的 key 会立即失效，并返回 HTTP 401（未认证）。所以接到 401 不一定是 key 写错了，也可能是它刚被吊销或过期。一个良好的实践是在 CI 里定期轮换 key（配合可选的过期时间），这样即使某把 key 泄露，暴露窗口也是有限的。
