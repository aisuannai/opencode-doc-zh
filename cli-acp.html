ACP

opencode acp 让 OpenCode 以 Agent Client Protocol（ACP）agent 的身份运行，从而可以从 Zed 等 ACP 客户端中使用它。本页前半是普通用户的使用指南，后半是面向 ACP 客户端作者的协议参考。

🧠 通俗理解

ACP 可以类比成「编辑器和 AI 助手之间的通用插座」：过去每个编辑器要为每个 AI 工具单独做适配，像各家各异的插头；ACP 规定了统一的电压和插孔，任何客户端（Zed、未来更多编辑器）都能用同一种方式驱动任何 agent。OpenCode 插上这个插座，就能直接住进 Zed 的侧边栏里干活。

在客户端中接入

以 Zed 为例，把 OpenCode 加进它的 agent 服务器列表：

~/.config/zed/settings.json
{
  "agent_servers": {
    "OpenCode": {
      "command": "opencode",
      "args": ["acp"]
    }
  }
}

其它 ACP 客户端也使用同样的命令和 acp 参数，只是配置文件与字段名可能不同。如果图形客户端找不到 opencode，把 command 设为 which opencode 打印出的绝对路径。

鉴权

OpenCode 直接复用它已有的提供商凭据。启动 ACP 客户端之前，先在终端里登录：

bash
opencode auth login

OpenCode 只提供一种认证方法 opencode-login。默认它是 agent auth 方法：authenticate 请求只接受这一方法，且不收集凭据。当某个 prompt 因为提供商需要登录而失败时，OpenCode 返回 ACP 的 auth_required 错误。

如果客户端把 clientCapabilities.auth.terminal 设为 true，该认证方法就变成 terminal auth 方法：

json
{
  "id": "opencode-login",
  "name": "Login with opencode",
  "description": "Run `opencode auth login` in the terminal",
  "type": "terminal",
  "args": ["--login"]
}

此时客户端不得把该方法发给 authenticate，而应给启动 OpenCode 的命令加上 --login（例如 opencode acp --login）并在终端里运行。OpenCode 会执行 opencode auth login 流程然后退出；退出码 0 表示登录成功。客户端随后重连并再次发送 initialize。

如果客户端把 clientCapabilities._meta["terminal-auth"] 设为 true，认证方法里会附带登录命令：

json
{
  "id": "opencode-login",
  "name": "Login with opencode",
  "description": "Run `opencode auth login` in the terminal",
  "_meta": { "terminal-auth": { "command": "opencode", "args": ["auth", "login"], "label": "OpenCode Login" } }
}

故障排查

opencode acp 在 stdin 上等待 ACP 消息，所以直接在终端里运行它时看起来像卡住了——请改从 ACP 客户端启动它。

如果客户端报告进程退出了、或输出了无效的协议数据，可以在客户端参数里把 --print-logs 加到 acp 之前。此后 OpenCode 会把 ACP 日志和私有服务器日志写到 stderr，而 stdout 只承载 ACP 消息：

bash
opencode --print-logs acp

⚠️ 注意

「直接运行 acp 看起来卡死」不是 bug：它就是在等管道里进消息。同理，--print-logs 必须放在 acp 子命令之前（opencode --print-logs acp），写错位置会被当成 acp 的未知参数。

协议参考

本节面向 ACP 客户端作者，列出 OpenCode 支持的 ACP 部分以及 OpenCode 添加的 _meta 键。不认识这些键的客户端可以忽略它们。消息定义见 ACP 文档。

传输层

客户端把 opencode acp 作为子进程启动，双方通过 stdin 和 stdout 交换按行分隔的 JSON-RPC 消息，使用 ACP 协议版本 1。

opencode acp 会为自用启动一个私有的 OpenCode 服务器；它不连接共享后台服务，也不为 ACP 打开网络端口。一个进程可以同时服务多个 ACP 会话。客户端关闭 stdin 时进程退出。

能力

OpenCode 的 initialize 响应包含以下 agent 能力：

json
{
  "loadSession": true,
  "mcpCapabilities": { "http": true, "sse": false },
  "promptCapabilities": { "embeddedContext": true, "image": true },
  "sessionCapabilities": {
    "additionalDirectories": {},
    "close": {},
    "delete": {},
    "fork": {},
    "list": {},
    "resume": {}
  }
}

OpenCode 会读取以下客户端能力：

能力效果
auth.terminal 设为 true认证方法成为 terminal auth 方法。
elicitation.formOpenCode 以表单形式提问（见下文）。
session.compactionOpenCode 通过 ACP 更新上报压缩进展。
_meta["terminal-auth"] 设为 true认证方法中附带登录命令。

会话

客户端在创建会话时设定工作目录。OpenCode 使用该目录的配置，包括其中的模型、agent、命令、skills、instructions、插件和 MCP 服务器。

  • cwd 必须是绝对路径；传入相对路径会收到 invalid params 错误。
  • session/load 会重放已保存的消息；session/resume 和 session/fork 不重放。
  • 要 load、resume 或 fork 一个会话，客户端必须把该会话所在的目录作为 cwd 传入；传别的目录会收到 invalid params 错误。
  • session/list 每页最多返回 100 个会话，接受 cwd 过滤器和 cursor。
  • session/close 会中断正在执行的工作，并把会话从 ACP 进程分离。OpenCode 保留已保存的会话。
  • session/delete 先像 session/cancel 一样结束进行中的 prompt，然后移除会话。删除不存在的会话也会成功。
  • 一个会话同一时间只跑一个 prompt。第一个 prompt 还在进行时再发 session/prompt，OpenCode 会返回错误。

取消

session/cancel 以 stopReason: "cancelled" 结束进行中的 prompt；对 prompt 请求发 $/cancel_request 效果相同。OpenCode 会拒绝仍在等待的权限请求，并把取消后未完成的工具调用报告为 failed。

附加目录

客户端可以在 session/new、session/load、session/resume、session/fork 上传 additionalDirectories：

json
{ "cwd": "/work/app", "additionalDirectories": ["/work/shared"], "mcpServers": [] }
  • 每一项必须是绝对路径，且不含 * 或 ?。
  • OpenCode 允许在每个根之内访问外部目录；读取、编辑和 shell 的权限规则仍然生效。
  • 每次请求携带的列表会替换会话之前的列表，与 additional directories RFD 的规定一致。
  • OpenCode 把授权存储在会话上，因此其它 OpenCode 客户端使用该会话时同样生效；创建子会话时，授权会被复制进去。

session/list 会在 additionalDirectories 中返回每个会话已存储的列表。

配置选项

新会话使用所在目录的默认模型和主 agent。session/new、session/load、session/resume、session/fork 的响应包含这些配置选项：

ID类别可选值
modelmodel启用的模型，格式 provider/model。加 /variant 后缀还能同时设置 effort。
effortthought_level该模型的各 variant 和 default。仅在有 variant 的模型上出现。
modemode可见的主 agent。

session/set_config_option 接受字符串值：

json
{ "sessionId": "ses_123", "configId": "model", "value": "anthropic/claude-sonnet-5-5" }

session/set_mode 同时设置 agent。当可用模型或 agent 变化时，OpenCode 会发送 config_option_update；其它客户端改变会话的模型或 agent 时也会发一次。

Prompt 内容

Prompt 可以包含文本、图片、嵌入式资源和资源链接。OpenCode 忽略音频块，其它块的处理方式如下：

块OpenCode 的处理
text发给模型。
text（audience 仅为 assistant）作为独立上下文发给模型，放在用户消息之外。
text（audience 仅为 user）不进入模型输入。
带 data 的 image附加到 prompt。
仅有 uri 的 image按资源链接处理。
带 text 的 resource把文本内联到资源的路径或 URI 之后。
带 blob 的 resource有 mimeType 就附加，否则丢弃。
指向 file:// URI 的 resource_link附加该文件。文件缺失或不可读时改为发送 Markdown 链接。
指向带 path 查询的 zed:// URI 的 resource_link附加 path 处的文件。
指向其它 URI 的 resource_link发送 Markdown 链接，例如 [spec](https://example.com/spec.md)。

audience 来自块的 annotations。既没有 data 也没有 uri 的 image 块会被拒绝。下面这个块只作为模型的上下文：

json
{ "type": "text", "text": "Open file: src/app.ts", "annotations": { "audience": ["assistant"] } }

命令

在 session/new、session/load、session/resume 或 session/fork 之后，OpenCode 发送 available_commands_update，包含该目录的命令和内置的 compact 命令。命令变化时会再次发送更新：

json
{
  "sessionUpdate": "available_commands_update",
  "availableCommands": [{ "name": "compact", "description": "Compact the session" }]
}

如果 prompt 以 / 加某个可用命令的名字开头，OpenCode 就执行该命令，其余文本作为参数。其它以 / 开头的文本按普通 prompt 发送。/compact 执行上下文压缩。

MCP 服务器

客户端可以在 session/new、session/load、session/resume、session/fork 上传 stdio 和 HTTP MCP 服务器。OpenCode 会把它们加到会话目录上，有效期与 opencode acp 进程一致，因此该目录里的其它会话也能使用。OpenCode 会透传 HTTP 请求头，不对这些服务器使用 OAuth；不提供 SSE 方式的 MCP，也不支持 ACP 之上的 MCP。

情况行为
与已配置服务器同名客户端的服务器在该目录中替换已配置的那个。
策略integration.use 规则仍然生效。
json
{ "type": "http", "name": "docs", "url": "https://mcp.example.com", "headers": [] }

权限

权限请求提供三个选项：

json
[
  { "optionId": "once", "kind": "allow_once", "name": "Allow once" },
  { "optionId": "always", "kind": "allow_always", "name": "Always allow" },
  { "optionId": "reject", "kind": "reject_once", "name": "Reject" }
]

当请求会修改文件时，如果 OpenCode 能构建改动的预览，就会附带 diff 内容。

提问

如果客户端声明了 elicitation.form，OpenCode 会用 elicitation/create 以表单模式提问。当 OpenCode 曾把某个工具调用作为 session/update 发出时，请求会带上 toolCallId：

json
{
  "mode": "form",
  "sessionId": "ses_123",
  "toolCallId": "call_1",
  "message": "Which package manager?",
  "requestedSchema": {
    "type": "object",
    "properties": { "pm": { "type": "string", "oneOf": [{ "const": "bun", "title": "Bun" }] } },
    "required": ["pm"]
  }
}
  • OpenCode 永远不会发送可能收集密钥的表单。
  • 如果某字段在选项之外还接受自由输入，schema 会加一个可选的 <key>_custom 字符串属性。单选题里，非空的自定义答案会替换已选选项；多选题里，自定义答案会追加到已选选项。
  • 用户拒绝或取消表单时，OpenCode 会取消这个问题。

如果 OpenCode 无法展示问题，它会取消问题并让模型在没有答案的情况下继续。

压缩

如果客户端声明了 session.compaction，OpenCode 会用 ACP session compaction RFD（处于 Preview 阶段）中的 compaction_update 和 compaction_summary_chunk 更新来上报压缩进展。客户端加载会话时，OpenCode 会把每一次已完成或失败的压缩各重放为一条更新：

json
{
  "sessionUpdate": "compaction_update",
  "compactionId": "msg_123",
  "status": "completed",
  "summary": [{ "type": "text", "text": "..." }]
}

其它客户端会收到压缩标记；子会话的压缩也一样用标记。

用量

Prompt 响应包含 end-turn usage RFD（草案）中的 usage。usage 汇总本会话中该 prompt 的所有模型调用，不含子会话：

json
{ "stopReason": "end_turn", "usage": { "inputTokens": 1200, "outputTokens": 340, "totalTokens": 1540 }, "_meta": {} }

响应之前，OpenCode 会发送 session usage RFD 中的 usage_update；仅当 prompt 消耗了 token 且 OpenCode 知道模型上下文大小时才发送。cost 是会话的累计费用（美元）：

json
{ "sessionUpdate": "usage_update", "used": 1540, "size": 200000, "cost": { "amount": 0.012, "currency": "USD" } }

子会话

Prompt 运行期间，OpenCode 把子会话的更新作为 session/update 通知发到该 prompt 的会话上。每条更新携带 _meta["opencode/child-session"]。OpenCode 会给工具调用 ID 加上 <childSessionId>: 前缀；如果子会话有标题，工具调用标题也会加该标题前缀：

json
{
  "sessionUpdate": "tool_call",
  "toolCallId": "ses_child:call_1",
  "title": "Explore the codebase: src/app.ts",
  "_meta": {
    "opencode/child-session": { "id": "ses_child", "parentID": "ses_123", "depth": 1, "title": "Explore the codebase" }
  }
}
字段类型说明
idstring子会话的 ID。
parentIDstring子会话父会话的 ID。
depthnumberprompt 会话的直接子会话为 1，孙会话为 2，依此类推。
titlestring子会话的标题；子会话没有标题时省略。

来自子会话的权限请求会在 toolCall._meta 上带同样的键。Prompt 结束后，OpenCode 停止发送子会话更新；但子会话的权限请求和提问仍然会到达客户端。

重试状态

当模型调用失败并安排重试时，OpenCode 发送带 _meta["opencode/retry"] 的 session_info_update。重试开始时发送 "opencode/retry": null。客户端应在收到 prompt 响应时清掉重试状态：

json
{
  "sessionUpdate": "session_info_update",
  "_meta": {
    "opencode/retry": {
      "attempt": 1,
      "nextRetryAt": "2026-10-02T12:00:05.000Z",
      "error": { "type": "provider.rate-limit", "message": "Rate limit exceeded", "status": 429 }
    }
  }
}
字段类型说明
attemptnumber重试的序号。
nextRetryAtstring下次尝试的时间，ISO 8601 格式。
errorobject含 type 和 message；提供商给出时还有 status 和 response.body。

压缩标记

如果客户端没有声明 session.compaction，OpenCode 用带 _meta["opencode/compaction"] 的 session_info_update 上报压缩进展。子会话的压缩则总是使用标记：

json
{
  "sessionUpdate": "session_info_update",
  "_meta": { "opencode/compaction": { "status": "started", "messageId": "msg_123", "reason": "auto" } }
}
字段类型说明
statusstringstarted、completed 或 failed。被取消的压缩记为 failed。
messageIdstring把一次压缩的开始和结束配对。请把它当作不透明的 key 处理。
reasonstringauto 或 manual。
errorobjectstatus 为 failed 时出现，结构与重试的 error 相同。

标记不含摘要。自动压缩可能在没有 started 标记的情况下直接失败。客户端加载会话时，OpenCode 把每一次已完成或失败的压缩各重放为一条标记。

💡 扩展

「压缩更新 vs 压缩标记」的二选一设计值得留意：声明了 session.compaction 能力的客户端拿到带摘要内容的细粒度更新（可以做进度条和摘要预览）；没声明的只收到轻量的状态标记（适合只显示「正在压缩…」的客户端）。实现客户端时按自己界面的精细程度选择声明哪个能力即可。
