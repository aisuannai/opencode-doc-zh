上下文压缩

压缩（Compaction）用一个摘要替换较早的对话，给长会话腾出空间，让会话能一直用到超过模型的上下文上限。

工作原理（How it works）

当会话接近模型的上下文上限时，OpenCode 会把当前的整段对话总结成一份摘要。同时它会在摘要旁边保留最近的对话（默认约 15,000 token），让最近的精确细节仍然可用：

text压缩前后对比
before   [ system prompt ][ older conversation ............ ][ recent 15k ][ pending work ]
request  [ system prompt ][ older conversation ............ ][ recent 15k ][ summary instructions ]
after    [ system prompt ][ summary of older + recent ][ recent 15k ][ pending work ]

发送完整对话来生成摘要，可以在提供商支持时复用正常请求的提示词缓存（prompt cache）。之后的每次压缩都会用「自上次检查点以来的对话」更新已有摘要。

开始压缩（Start）

自动压缩默认开启：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "compaction": {
    "auto": true,
    "keep": { "tokens": 15000 },
  },
}

⚠️ 注意

压缩是有损的（lossy）——摘要不可能逐字保留所有细节。最近的精确细节很重要时，调大 keep.tokens；或者赶在自动压缩之前自己手动触发一次。

手动压缩（Manual）

可以随时请求压缩，即使历史很短：

sh
opencode api post /api/session/ses_example/compact --data '{}'

api 命令会发现后台服务并完成认证。它的响应只确认请求被接受，不会等摘要生成完。关注 session.compaction.* 事件来了解它何时完成。完整操作见 API 参考。

规则行为
时机在下一个安全点运行，位于仍在等待的 prompt 之前。
重复请求已有一次压缩进行中时，新的请求会合并进去。
自动化compaction.auto 为 false 时手动请求仍然有效。

传入一个 id 可以让精确的重试具有幂等性。同一个 ID 用在另一个请求上会返回冲突：

sh
opencode api post /api/session/ses_example/compact --data '{"id":"msg_compact_once"}'

设置（Settings）

在任意 OpenCode 配置文件里加 compaction：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "compaction": {
    "auto": false,
    "keep": { "tokens": 24000 },
    "buffer": "20%",
  },
}
字段默认行为
autotrue在接近上下文上限时自动压缩；当提供商拒绝「请求过长」时自动恢复一次。手动压缩始终可用。
backgroundtrue提前写好摘要，让自动压缩不用现场等待。见「后台压缩」一节。
keep.tokens15000摘要旁保留的最近对话的近似 token 数。值越大细节保留越多，但留给新工作的空间越少。
buffer"15%"，至少 16k模型上下文窗口中保留空闲的比例。对话到达其余部分时自动压缩启动。值越大压缩越早。

keep.tokens 接受非负整数。

Buffer（缓冲区）

buffer 是每个模型窗口的百分比，所以一个设置适配所有模型：

模型窗口"buffer": "20%" 时压缩点
128k约 102k
1M800k
  • 它表示保留空闲的空间，不是压缩启动点："20%" 表示窗口装到 80% 时压缩。
  • 接受 "1%" 到 "99%"，包括 "12.5%" 这样的小数。
  • 也可以直接给 token 数，如 20000。同一个数字在小窗口里占很大比例，在大窗口里只占很小比例。
  • token 数大于等于模型窗口时会被忽略，回退到默认值。

摘要模型（Model）

默认由 OpenCode 用会话自己的模型写摘要。设置 agents.compaction.model 可以换一个模型来写摘要：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "agents": {
    "compaction": { "model": "anthropic/claude-sonnet-5-5" },
  },
}

如果该模型无法解析，OpenCode 回退到会话的模型。

后台压缩（Background compaction）

OpenCode 会提前写好摘要——会话继续运行——等压缩时机到了再换入。这样自动压缩就不需要暂停会话现场写摘要：

text时序示意
60k tokens before the threshold   summary of the conversation so far starts in the background
                                  the session keeps going; the summary is held, not applied
threshold                         the held summary is swapped in; everything since it is kept as is

在小上下文窗口上，摘要最早在「上次压缩后第一条响应」与「阈值」之间的一半处启动。

规则行为
成本摘要请求复用提示词缓存。一份从未被用上的摘要（比如会话在到达阈值前就结束了）仍然消耗 token。
等待压缩时机到了而摘要还没写完时，会话会等它写完。
回退当「持有的摘要之后的新增对话」超过阈值约 40%，或者对话的开头发生了变化时，压缩改为照常重新总结。
跳过原生压缩（native compaction）不使用它。刚切换模型后，或中断时间超过提示词缓存时长后，从下一条响应开始才启用。
存储持有的摘要只存在内存里，重启即丢失。

想只在压缩时机到了才写摘要，把它关掉：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "compaction": {
    "background": false,
  },
}

提供商侧压缩（Providers）

有些提供商可以在它们那边压缩对话。用 settings.compaction 按提供商或按模型开启：

opencode.jsoncJSONC
{
  "$schema": "https://opencode.ai/config.json",
  "providers": {
    "openai": {
      "settings": { "compaction": { "type": "native" } },
      "models": {
        "gpt-6.1-sol": { "settings": { "compaction": { "type": "summary" } } },
      },
    },
  },
}

模型设置优先于提供商设置。native 使用提供商的压缩；summary 使用 OpenCode 自己的摘要压缩。

使用原生压缩时，OpenCode 把对话发送到提供商的压缩端点，提供商返回一个不透明的加密数据项来「顶替」较早的对话。你的最近消息和附件（最多 keep.tokens）会与它并排保留：

text前后对比
before   [ older conversation ........................ ][ recent user messages ]
after    [ encrypted checkpoint + recent user messages ]
主题行为
支持OpenAI Responses 系模型。支持程度因部署和模型而异。
阈值与摘要压缩使用相同的 auto 和 buffer 设置。手动请求也可用。
可移植性加密检查点只能在同一提供商同一模型上使用。切换模型后，会话改为从原始对话继续。
过长提供商以「过长」拒绝一次压缩时，OpenCode 会用更小的请求重试，不会切换成摘要压缩。

摘要长什么样（Summaries）

摘要是结构化的，好让另一个智能体能从它接手工作：

md摘要结构示例
## Objective
Finish the authentication migration.

## Next Move
- Update the callback handler.
- Verify the login flow.

它涵盖目标与需求、已做的决定、已完成和进行中的工作、阻塞点与下一步动作、相关文件。在保留的最近对话里，过长的工具输出会被缩短，附件数据会被替换成一句简短描述。

压缩之后，你的指令文件（instruction files）的当前版本会成为会话的新基线；见 指令文件。

限制（Limits）

限制结果
模型摘要压缩遵循 agents.compaction.model，否则用会话的模型。原生压缩始终用会话的模型。
历史压缩需要「较早的对话」才有东西可替换。当请求几乎全是固定指令和工具 schema 时，压缩腾不出空间。
大小要压缩的对话本身太长时，OpenCode 会发送缩短的文字版，并可能省略最早的几轮交流。
恢复被拒绝为「过长」的请求会压缩后重试一次。第二次仍被拒绝则作为错误返回。
存储较早的消息即使不再发送给模型，也仍然保留在存储中。

比如这种场景压缩也帮不上忙：

text
128k context = 120k fixed instructions and tools + 8k conversation

🧠 通俗理解

把上下文窗口想成一张桌子：128k 的桌子坐满了（大段历史、长篇工具输出），新的活就没地方摊开。压缩就是一位「会议记录员」：把前几小时的讨论整理成一页纪要（摘要），桌上只留纪要 + 最近 15k 的对话细节。会议可以无限开下去，但「纪要写不掉的桌布」（固定的系统提示词和几十个工具 schema）始终占着位置——所以固定开销太大的会话，压缩也救不了。

从 V1 迁移（Migration）

V1 使用尾部轮转（tail-turn）和剪除（pruning）行为。V2 使用摘要和 compaction.keep.tokens：

jsonc
{
  "compaction": {
    "keep": { "tokens": 15000 }
  }
}

本页介绍的设置和行为都适用于 V2。
