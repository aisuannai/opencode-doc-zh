网络

在公司代理、自签名证书、杀毒软件 HTTPS 拦截这些环境下 OpenCode 连不上模型？这一页讲清楚怎么设置代理变量、信任企业证书、配置客户端证书，以及如何验证连通。

基础代理设置

设置标准的代理变量并排除回环地址（loopback）。OpenCode 在 CLI 和后台服务之间使用本地 HTTP 连接，所以在 CLI 环境里配置了代理时，回环排除是必需的：

bash
export HTTP_PROXY=http://proxy.example.com:8080
export HTTPS_PROXY=http://proxy.example.com:8080
export NO_PROXY=localhost,127.0.0.1,::1

opencode

HTTP_PROXY 处理 HTTP 目标，HTTPS_PROXY 处理 HTTPS 目标。代理 URL 本身对两个变量都可以用 http://。NO_PROXY 是一个逗号分隔的主机和地址列表，它们直连不走代理。

后台服务（Service）

shell 里 export 的变量只有当后台服务从那个 shell 启动时才对它生效。把变量持久化到托管服务配置里，以后每次启动服务都会用同样的网络设置：

bash
opencode service set env HTTP_PROXY http://proxy.example.com:8080
opencode service set env HTTPS_PROXY http://proxy.example.com:8080
opencode service set env NO_PROXY localhost,127.0.0.1,::1
opencode service start

修改托管环境变量会停止正在运行的服务；service start 会用新环境重新启动。当 CLI 所在的 shell 设置了代理时，记得在 shell 里也保留 NO_PROXY——因为托管服务的变量只作用于服务器进程，不作用于 CLI 进程。

用 service unset env 移除一个持久化的变量：

bash
opencode service unset env HTTPS_PROXY

代理认证（Authentication）

对于接受 URL 凭据的代理，把用户名和密码写进每个需要认证的代理 URL。凭据中的 @、:、/ 等字符要做百分号编码：

bash
export HTTPS_PROXY='http://user:p%40ssword@proxy.example.com:8080'

对后台服务，要持久化完整的 URL。该值保存在私有的服务配置中，并且可以通过 opencode service get env 查看——所以不要把那个输出分享出去：

bash
opencode service set env HTTPS_PROXY 'http://user:p%40ssword@proxy.example.com:8080'

证书（Certificates）

当代理或目标服务器使用由私有证书机构（CA）签发的证书时，把 NODE_EXTRA_CA_CERTS 指向一个 PEM 文件。进程启动时，这些额外的证书机构会被加入运行时信任库：

bash
export NODE_EXTRA_CA_CERTS=/etc/company/ca.pem
opencode --standalone

给后台服务持久化文件路径，然后重启：

bash
opencode service set env NODE_EXTRA_CA_CERTS /etc/company/ca.pem
opencode service start

杀毒软件与 HTTPS 检查

杀毒软件的「HTTPS 扫描」或「加密连接扫描」（Kaspersky、Avast、ESET 等）以及企业级 SSL 检查代理，会把服务器的证书换成它们自己的。OpenCode 会拒绝这种证书，请求失败并报类似这样的错：

text典型报错
self signed certificate in certificate chain
SELF_SIGNED_CERT_IN_CHAIN
CERT_NOT_YET_VALID
CERT_SIGNATURE_FAILURE

两种修复方式任选其一：

  • 在杀毒软件设置里，把 opencode.ai 和 *.opencode.ai 排除出 HTTPS 扫描。如果直连某个模型提供商，把它 API 的主机也加上，如 api.anthropic.com。
  • 把检查用的证书机构导出为 PEM 文件，用 NODE_EXTRA_CA_CERTS 信任它，见上文「证书」一节。

⚠️ 注意

看到 SELF_SIGNED_CERT_IN_CHAIN 这类报错，第一反应不该是「关掉证书校验」，而是搞清楚是谁在中间换了证书。公司机器上几乎都是杀毒软件或 SSL 检查代理干的，按上面两种方式处理即可；不要用 NODE_TLS_REJECT_UNAUTHORIZED=0 之类的方式绕过校验，那会让所有连接失去中间人防护。

客户端证书（Client certificates）

当提供商的网关要求双向 TLS（mTLS）时，在该提供商上设置 settings.tls。它的模型请求会出示客户端证书，TLS 握手只会把证书发给请求证书的服务器：

opencode.jsoncJSONC
{
  "providers": {
    "company": {
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "https://llm.company.example/v1",
        "tls": {
          "cert": "{file:/etc/company/client.pem}",
          "key": "{file:/etc/company/client.key}",
          "passphrase": "{env:CLIENT_KEY_PASSPHRASE}",
        },
      },
    },
  },
}
  • cert 和 key 是 PEM 文本。用 {file:...} 从文件读取。文件读不到时 tls 保持未设置。
  • passphrase 只在密钥加密时需要。
  • 在 Bun 和 Node 构建上可用。跑在 Cloudflare Workers 上的服务器无法通过 fetch 出示客户端证书。
  • 带客户端证书的请求不跟随重定向，所以证书不会发给另一个主机。

该提供商的每个模型请求都会出示证书：chat、compaction、图像和决策模型都算。设置了 tls 的提供商用 HTTP 而不是 WebSocket。webfetch、远程 MCP 服务器、插件安装等工具不出示它。

前台进程（Foreground）

--standalone 和 serve 使用自己进程的环境变量，opencode service set env 不会配置这些进程：

bash
HTTP_PROXY=http://proxy.example.com:8080 \
HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode --standalone

对前台服务器套用同样的模式：

bash
HTTPS_PROXY=http://proxy.example.com:8080 \
NO_PROXY=localhost,127.0.0.1,::1 \
opencode serve

验证（Verify）

应用设置后，先确认 CLI 能连上后台服务：

bash
opencode api get /api/info

健康检查成功说明「CLI → 服务」这一段本地连接是通的。再跑一次正常的提供商请求，验证「服务 → 外网」的出站代理和证书链路。

🧠 通俗理解

排查网络问题时把它想成两段水管：第一段是「CLI ↔ 本机后台服务」（永远走 localhost，所以代理变量一设置就可能把它也劫走——这就是必须配 NO_PROXY 的原因）；第二段是「后台服务 ↔ 互联网」（走你的代理和证书）。先用 opencode api get /api/info 验第一段，再用真实请求验第二段，坏在哪一段一眼就知道。
