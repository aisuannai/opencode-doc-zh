API · 提供商

你接入工作区的每个提供商（provider）都通过 Console 网关、以各自的 URL 对外服务。OpenCode 在执行 /connect 之后会自动使用它；你也可以直接调用，从而在自己的工具里用上同样的提供商。

bash最小可运行示例
curl -X POST "https://opencode.ai/inference/custom/conn_.../chat/completions" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "deepseek-v4.1-flash",
    "messages": [{ "role": "user", "content": "Say hi" }]
  }'

🧠 通俗理解

这个 API 本质上是一个「带钥匙的快递中转站」：你把请求寄到 Console 网关（https://opencode.ai/inference/custom/<connection_id>），Console 在转发前替你塞进真正的提供商密钥，再原样送到提供商那里。好处有二：一是你自己的工具不用管理各家密钥，只用一个 OpenCode key；二是提供商的机密凭证永远不会离开工作区，泄密面大幅缩小。

提供商 URL（Provider URL）

在 Providers 下的提供商页面里，复制它的 Console API URL：

text
https://opencode.ai/inference/custom/<connection_id>

认证（Authentication）

把 <token> 替换为在 Console 中创建的服务账号 key。Console 在转发之前会把它换成该连接自己的凭证：

text
Authorization: Bearer <token>

Console 也能从 x-api-key、api-key 或 x-goog-api-key 读取 key，所以把提供商官方 SDK 的 base URL 指向 Console API URL 也能直接工作。

⚠️ 注意

两个易错点：一，认证用的必须是 OpenCode 的 key（个人 key 或服务账号 key），千万别在这里填提供商自己的密钥——它会由网关在转发时自动注入；二，请求体里的 model 要写提供商页面上显示的模型 ID。当模型在上游（提供商原生 API）使用不同的 API ID 时，Console 会自动改写，但未在该连接上启用的模型会被直接拒绝。

端点（Endpoints）

把提供商的 API 路径拼接到 Console API URL 后面即可。Console 会把请求转发到该连接的 base URL，并原封不动地返回提供商的响应：

格式路径
Chat Completions/chat/completions
Responses API/responses
Anthropic Compatible/messages
Google Generative AI/models/<model>:generateContent

Chat Completions

bash
curl -X POST "https://opencode.ai/inference/custom/conn_.../chat/completions" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "deepseek-v4.1-flash",
    "messages": [{ "role": "user", "content": "Say hi" }]
  }'

Responses API

bash
curl -X POST "https://opencode.ai/inference/custom/conn_.../responses" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-6.1-sol",
    "input": "Say hi"
  }'

Anthropic Compatible

注意 max_tokens 是必填项：

bash
curl -X POST "https://opencode.ai/inference/custom/conn_.../messages" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "claude-sonnet-5-5",
    "max_tokens": 1024,
    "messages": [{ "role": "user", "content": "Say hi" }]
  }'

Google Generative AI

模型名和方法名都在路径里。把 :generateContent 换成 :streamGenerateContent 即可流式接收响应：

bash
curl -X POST "https://opencode.ai/inference/custom/conn_.../models/gemini-4-argon:generateContent" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "contents": [{ "parts": [{ "text": "Say hi" }] }]
  }'

💡 扩展

由于 Console 返回的是「提供商响应原样」，你可以把现有代码里指向 api.openai.com / Anthropic / Gemini 的 base URL 直接换成 Console API URL，其余逻辑零改动。四种格式（Chat Completions、Responses、Anthropic Compatible、Google Generative AI）覆盖了主流 SDK 的接入姿势，等于一次接入、处处可用。

用量（Usage）

请求会按每个模型上设定的价格计入预算（budgets）。token 费用由提供商直接向你收取。

🧠 通俗理解

计费是「两条腿」：提供商按它自己的价目表向你的账户（也就是连接里配置的那个账号）收 token 钱；同时 Console 会按模型上标定的价格把用量记到你工作区的预算里，方便控制和审计。也就是说，走这个 API 花的是提供商侧的钱，占的是你工作区预算的额度，两本账要分开看。
