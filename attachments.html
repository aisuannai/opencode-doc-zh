附件

把本地文件作为附件（Attachment）挂到提示词里，让 OpenCode 直接基于它回答：总结 README、看图写代码、读 PDF 出结论，都靠这一节讲的东西。

附加文件

先附加本地文件，然后在提示词里让 OpenCode 使用它。在桌面端或 Web 客户端里，点 Attach file（附加文件）、直接粘贴文件、或把它拖进输入框。

text
Summarize the attached README.md and list the required setup steps.

桌面端文件选择器一次最多可选共 20 MiB 的文件；其它界面可能有更低的客户端上限。

⚠️ 注意

附加图片前，先确认当前模型支持图片输入。OpenCode 能把受支持的图片传给提供商，但提供商和模型自己仍然会检查格式、尺寸、文件数量和大小限制。纯文本模型可能直接拒绝带图请求。

语法

V2 的提示词和命令输入用 uri 描述一个附件，可选 name 和 description：

json
{
  "uri": "file:///home/me/project/src/server.ts",
  "name": "server.ts",
  "description": "HTTP server entrypoint"
}

对服务器可访问的文件或目录，使用绝对 file: URL。对文本文件，正数的 start 和 end 参数可以选取行号（从 1 开始）范围内的内容：

text
file:///home/me/project/src/server.ts?start=20&end=60

用 data: URL 可以把内容内联发送：

json
{
  "uri": "data:text/plain;base64,SGVsbG8sIE9wZW5Db2RlIQ==",
  "name": "greeting.txt"
}

不支持 HTTP / HTTPS 的附件 URL。程序化提交提示词请见生成的 API 参考。

支持的格式

当前 V2 会话会把以下附件类型以可见形式交给模型：

输入模型收到示例
UTF-8 文本文件文件名 + 解码后的文本README.md
目录直接子级文件和目录的非递归列表file:///home/me/
PNG、JPEG、GIF 或 WebP图片媒体diagram.png
PDF文档媒体report.pdf

PDF 需要支持 PDF 输入的模型。如果模型不支持某种附件类型，OpenCode 会用一段简短说明文字代替它。

SVG 按文本处理。AVIF、BMP、音频、视频以及其它二进制提示词附件不会进入模型请求。先把不支持的二进制转换成文本或受支持的图片再附加——比如 BMP 图片应先转成 PNG。

OpenCode 会在提示词进入会话前读取每个附件，并拒绝以下情况：无效的 URL、读不了的路径、既不是文件也不是目录的路径、解码后超过 20 MiB 的附件。媒体类型按字节内容检测，所以改文件名或改 data: URL 的媒体类型，都无法让不受支持的二进制「伪装」成功。

图片设置

在 opencode.json / opencode.jsonc 里配置图片归一化：

opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "media": {
    "image": {
      "auto_resize": true,
      "max_width": 2000,
      "max_height": 2000,
      "max_base64_bytes": 5242880,
    },
  },
}

所有字段都是可选的：

字段默认值行为
auto_resizetrue超过限制的图片自动缩放；设为 false 时直接拒绝该图片。
max_width2000最大宽度（像素），必须为正整数。
max_height2000最大高度（像素），必须为正整数。
max_base64_bytes5242880Base64 编码后的最大字节数，必须为正整数。

比如，下面这组设置会把宽于 1200 像素的图片直接拒绝而不是缩放：

opencode.jsonc
{
  "media": {
    "image": {
      "auto_resize": false,
      "max_width": 1200,
    },
  },
}

这些设置同时作用于两类图片：用户附加到提示词里的受支持图片，以及内置 read 工具返回的图片。

处理流程

read 工具按字节内容识别 PNG、JPEG、GIF 和 WebP，最多读取 20 MiB 的原始图片数据，并按配置的图片限制检查宽、高和 Base64 长度。

auto_resize: true 时，OpenCode 保持宽高比，把图片缩到尺寸上限以内，然后逐级尝试更小的 PNG 和 JPEG 编码，直到满足 Base64 上限——所以输出的媒体类型可能变化。

text
Input:  4000 × 2000 WebP
Limits: 2000 × 2000
Output: 2000 × 1000 PNG or JPEG

如果没有任何编码能满足限制，处理就失败。设为 auto_resize: false 时，超过任一限制的图片原样拒绝；无法解码的图片同样失败。

text
Input:  2400 × 1600 JPEG
Limit:  max_width = 2000, auto_resize = false
Result: Image processing fails

如果图片缩放器不可用，OpenCode 会原样传递图片。因此图片设置是处理上限，不是上传边界或安全边界。

🧠 通俗理解

图片为什么要「归一化」？因为大多数模型对图片输入有尺寸和 token 开销限制：一张 4000×2000 的截图直接喂进去，要么被模型拒绝，要么烧掉大量 token。OpenCode 的做法像「登机行李托运」——超规格的行李帮你压缩到可托运的尺寸再送上飞机（auto_resize: true），或者干脆在值机口拒绝（auto_resize: false）。默认策略是前者，尽量别让你的图半路被退回来。

限制一览

限制项取值或行为示例
直接附件每项解码后 20 MiB；客户端可能有更低限制两个 12 MiB 文件可各自通过单项限制
桌面端选择器一次选择总共 20 MiB两个 12 MiB 文件超过选择上限
max_base64_bytes只计编码后的 Base64，不含完整 data: URL 前缀SGVsbG8= 算 8 字节
提供商图片限制在 OpenCode 处理之后再应用提供商可能拒绝已被 OpenCode 接受的图片
文本附件的模型要求不要求多模态模型notes.txt 以提示词文本形式插入
read 的文本限制使用独立的分页与截断限制大日志文件分页读取

⚠️ 注意

客户端接受了文件 ≠ 内容真的进了模型。附件必须是模型可见的格式，并且同时满足 OpenCode 和提供商两边的限制，内容才会真正到达模型。排查「AI 说没看到图」时，按这个顺序检查：模型是否支持该类型 → 文件是否超过 20 MiB → 是否被 auto_resize: false 拒掉 → 提供商自身限制。
