故障排查

OpenCode 采用客户端-服务器架构：后台服务器掌管会话、插件、权限等应用状态。排查问题的第一步，是判断问题出在客户端、共享服务器，还是某个具体项目上。

🧠 通俗理解

你可以让 OpenCode 自己排查自己。把问题描述给它，让它读这一页并按步骤操作——它能检查自己的服务和日志，帮你定位问题。这就像车坏了不用光猜，直接让车载诊断仪自己跑一遍。

检查后台服务

查看当前服务器信息：

bash
opencode service status

验证它的 API 是否健康：

bash
opencode api get /api/info

如果服务卡住或不健康，重启它：

bash
opencode service restart

也可以显式停止和启动：

bash
opencode service stop
opencode service start

💡 扩展

OpenCode 通常会自动发现或启动共享后台服务，service 命令只在诊断其生命周期时才需要。日常「重启大法」一条 opencode service restart 就够。

放行浏览器来源

如果另一个来源（origin）的浏览器客户端因 CORS 连不上，把该客户端的来源加进服务配置：

bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors

使用精确的 HTTP 或 HTTPS 来源（必要时含端口），不带路径或尾斜杠。要放行多个来源，把逗号分隔的列表作为一个参数传入；每个来源两侧的空白会被裁掉：

bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"

service get cors 输出一个 JSON 数组。移除已配置的列表用：

bash
opencode service unset cors

设置或取消服务配置会停止后台服务；下次启动时读取新配置，可用 opencode service start 显式启动。

对前台服务器，每个额外放行的来源重复一次 --cors：

bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com

使用 serve --service 时，传入的 --cors 标志只为该进程覆盖持久化的列表；不带这些标志，服务模式使用持久化列表。CORS 不改变监听地址，也不绕过服务器认证。

调用 API 检查

api 命令使用本地服务发现和认证流程。它接受 HTTP 方法 + 路径，或 OpenAPI 操作 ID。

所有端点和操作 ID 见 API 参考。

用 --data / -d 传 JSON 请求体，用 --header / -H 加请求头。

⚠️ 注意

当没有兼容且健康的服务可用时，运行 opencode api 可能会启动后台服务。

读日志

已安装版本的日志写在：

text
~/.local/share/opencode/log/opencode.log

复现问题的同时跟踪日志：

bash
tail -f ~/.local/share/opencode/log/opencode.log

每行日志带进程 run ID 和 role 字段。会话、提供商、插件、权限和工具活动用 role=server 过滤：

bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log

抓取堆快照

在任意平台上给运行中的后台服务器写一份内存（堆）快照：

bash
opencode debug heap-dump

该命令会等到快照写完，然后打印路径：

text
/home/me/.local/share/opencode/log/heap-48213-2026-10-23T013012345Z.heapsnapshot

用 --directory 写到别处；目录不存在时服务器会创建：

bash
opencode debug heap-dump --directory ./snapshots
  • 它只使用已在运行的服务器，绝不会启动、替换或重启服务器。
  • 用 --server <url> 可以抓你自己用 opencode serve 启动的服务器；它有密码时设置 OPENCODE_PASSWORD。此时 --directory 是服务器所在机器上的路径。
  • 在 Chrome DevTools 的 Memory 面板里打开该文件。

⚠️ 注意

写快照期间服务器会暂停，内存占用可能短暂升高。快照里可能包含提示词、文件内容和凭证，不要公开发布。

桌面应用里

在命令面板里运行 Capture heap snapshots。它会在你的「下载」文件夹里写一个目录，包含应用各部分的快照，外加一份「快照看不到的内存」的分解：

text
opencode-heap-2026-10-23T013012345Z/
  memory.json                  where the memory is, per process, in MiB: start here
  memory-infra.json            Chromium's memory dump trace; open it in https://ui.perfetto.dev
  heap-48213-….heapsnapshot    the desktop's own server
  window-1-48390.heapsnapshot  one per app window
  main-48102.heapsnapshot      the desktop main process
  gpu.json                     the GPU and driver
  manifest.json                processes, PIDs, and memory before and after; written last
  • 堆快照只包含 JavaScript 对象和页面。图片、布局、合成器层和 GPU 内存在 memory.json 和 memory-infra.json 里。
  • 远程服务器不会被抓取。在那台机器上用 opencode debug heap-dump。
  • 服务器把快照直接写进文件夹，没有大规模的移动或复制。
  • 浏览器标签页不包含在内，因为它们的快照会包含你访问过的页面内容。

抓取 CPU 与内存剖析

在 macOS 和 Linux 上，可以给运行中的 OpenCode 进程发信号来采集诊断数据。先从健康端点拿到后台服务器的 PID：

bash
opencode api get /api/info

用响应里的 pid 发以下信号之一：

  • SIGPROF 抓一份 10 秒的 CPU 剖析：
    bash
    kill -SIGPROF <pid>

    结果写入日志目录，文件名为 cpu-<pid>-<timestamp>.cpuprofile。

  • SIGUSR1 抓一份内存（堆）快照：
    bash
    kill -SIGUSR1 <pid>

    结果写入日志目录，文件名为 heap-<pid>-<timestamp>.heapsnapshot。

等 opencode.log 里出现 CPU profile written 或 heap snapshot written 再打开文件；对应日志条目里有完整路径。两种文件都能在 Chrome DevTools 里查看。

⚠️ 注意

Windows 上没有信号触发的剖析。堆快照请改用 opencode debug heap-dump。写堆快照可能暂停进程并临时增加内存占用。

服务文件

共享服务器在以下位置注册自己：

text
~/.local/state/opencode/service.json

它的私有服务配置单独存放在：

text
~/.config/opencode/service.json

数据库通常位于：

text
~/.local/share/opencode/opencode.db

OPENCODE_DB 可以覆盖数据库位置。

⚠️ 注意

排查期间不要删除或编辑服务文件和数据库。管理守护进程用 service 命令；要用外部工具查看持久化数据前，先备份。

反馈问题

报告可复现问题时请附上：

  • opencode --version 的输出
  • opencode service status 的输出
  • 复现该问题的最小步骤序列
  • 问题影响的是共享服务、某个客户端，还是某一个项目
  • 相关日志行，包括其中的 run 和 role 字段

分享日志之前，去掉 API key、授权头、提示词、文件内容和其它敏感数据。

可复现的问题提交到 GitHub Issues。一份好的 issue 报告 = 版本号 + 服务状态 + 最小复现步骤 + 影响范围 + 相关日志，信息越精确，问题越可能被快速修掉。
