格式化器

OpenCode 可以在 write、edit、patch 工具改动文件之后自动格式化。格式化器（Formatter）默认关闭，需要在配置里手动启用。

🧠 通俗理解

智能体改完代码后，格式可能不太整齐（缩进、引号风格、换行）。格式化器就像一个「自动整理工位」的助手：每次 AI 写完或改完文件，OpenCode 会悄悄调用 Prettier、gofmt 这类工具把文件重新排一遍。你看到的永远是符合项目风格的代码，而不用在 review 时纠正 AI 的缩进。

启用

把 formatter 设为 true，即可启用全部内置格式化器。内置格式化器只有在对应的可执行文件和项目要求都就绪时才会真正运行。

opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "formatter": true,
}

把 formatter 写成对象也能启用内置格式化器，同时还可以覆盖它们、或添加自定义格式化器。空对象 {} 表示保留继承来的格式化器设置；而 true 表示重置为内置的那套。

opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "formatter": {},
}

⚠️ 注意

格式化器默认是关闭的。也就是说，即使你项目里装了 Prettier，不配置 formatter 时 OpenCode 也不会自动跑它。另外，内置格式化器是「按需触发」的：对应的命令（如 gofmt）不存在或项目依赖没装时，它会静默跳过，不会报错打断你。

举个例子：启用内置格式化器后，OpenCode 会自动发现并使用项目本地的 Prettier 依赖来处理匹配的文件：

opencode.jsonc
{
  "formatter": true,
}

💡 扩展

注意这张表的「前提条件」一列的两种模式：命令行工具（如 gofmt）要求装在系统 PATH 里；而 Prettier、Biome 这类则优先用项目本地依赖（node_modules 里的），保证用的是项目锁定的版本，而不是全局装的那份。所以「装了但版本不对」的问题基本不会出现。

自定义

在 formatter 对象里加一个具名条目，就可以覆盖内置格式化器或定义自定义格式化器。自定义格式化器必须同时提供 command 和 extensions 才能运行。

opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "formatter": {
    "prettier": {
      "environment": {
        "NODE_ENV": "development",
      },
      "extensions": [".js", ".ts"],
    },
    "deno-markdown": {
      "command": ["deno", "fmt", "$FILE"],
      "extensions": [".md"],
    },
  },
}
字段类型行为
disabledboolean为 true 时移除这个具名格式化器。
commandstring[]替换内置命令，或定义自定义命令。
environmentRecord<string, string>追加环境变量，父级环境变量仍然保留。
extensionsstring[]替换内置扩展名列表，或定义自定义列表。要带上前导点。

所有字段都是可选的。覆盖内置条目时，省略的字段沿用内置值；而一个新建条目如果没给 command 或 extensions，就无法运行。

opencode.jsonc
{
  "formatter": {
    "prettier": {
      "extensions": [".md", ".mdx"],
    },
  },
}

命令

command 是一个参数数组，不是 shell 命令字符串。OpenCode 会把 $FILE 替换成文件的绝对路径，并在当前项目目录下执行这条命令。

opencode.jsonc
{
  "formatter": {
    "custom": {
      "command": ["custom-fmt", "--write", "$FILE"],
      "extensions": [".custom"],
    },
  },
}

⚠️ 注意

不要把命令写成 "command": "prettier --write $FILE" 这样的整串字符串——它必须是数组。写成字符串会导致参数解析失败。另外 $FILE 是 OpenCode 替换的占位符，写的时候要原样保留，别自己填上真实路径。

匹配规则

OpenCode 用文件的最终扩展名与 extensions 对比。匹配区分大小写；像 .part.md 这类复合后缀，最终扩展名是 .md，所以不会匹配 extensions 里写了 .part.md 的条目。

opencode.jsonc
{
  "formatter": {
    "markdown": {
      "command": ["deno", "fmt", "$FILE"],
      "extensions": [".md"],
    },
  },
}

当多个格式化器都匹配同一个文件时，OpenCode 按注册顺序依次尝试，第一条命令成功后就停止。内置格式化器保持内置顺序；自定义条目按对象里的书写顺序排在后面。如果某条命令退出时失败，OpenCode 会记录失败并尝试下一个匹配项。

opencode.jsonc
{
  "formatter": {
    "preferred": {
      "command": ["preferred-fmt", "$FILE"],
      "extensions": [".foo"],
    },
    "fallback": {
      "command": ["fallback-fmt", "$FILE"],
      "extensions": [".foo"],
    },
  },
}

🧠 通俗理解

可以把匹配想象成「抢工作」：文件一改完，所有扩展名对得上的格式化器排成一队，前面的先上，成功了后面的人就回家。所以想让某个格式化器优先，把它写在对象靠前的位置即可；排在后面的自动变成兜底方案。

禁用

如果任何配置文件都没有设置 formatter，格式化就是关闭状态。要禁用某个低优先级文件启用的格式化，把它设为 false：

opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "formatter": false,
}

如果只想禁用某个内置格式化器、其余保持启用，把它的具名条目标记为 disabled：

opencode.jsonc
{
  "formatter": {
    "prettier": {
      "disabled": true,
    },
  },
}

💡 扩展

OpenCode 的配置支持多文件继承（全局配置 → 项目配置逐层覆盖），格式化器也遵守这套规则：true 重置为内置、{} 保留继承、false 整体关掉。调试格式化问题时，先用 opencode debug config 看看最终生效的配置是什么，能省掉很多「为什么没生效」的困惑。详见 配置一章。
