策略

策略（Policy）决定 OpenCode 是否可以对某个具名资源执行动作。它们写在 policies 配置下，也可以由已连接的 OpenCode Console 工作区下发。

🧠 通俗理解

策略和权限是两套不同层级的门禁：权限是「保姆级的规则」——针对具体工具动作，可以弹窗询问你；策略是「铁闸门」——一刀切、从不弹窗，只收紧不放宽。策略适合场景：公司统一规定「谁都不许用 OpenAI」「不许执行 git push」——这种要求要能压过用户和项目自己的配置，就必须用策略。

策略独立于权限。权限是按智能体（agent）生效的工具规则，可以有 allow、deny、ask 三种结果。策略是二元的、从不提示，且只会收紧权限和提供商原本允许的范围。

配置

在 opencode.jsonc 里加一条语句，就能在所有地方禁用一个提供商：

opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "policies": [{ "action": "provider.use", "resource": "openai", "effect": "deny" }],
}

被禁用的提供商会从目录和模型选择里消失，即使它有有效凭证。

早期版本从 experimental.policies 读取策略。该键仍然有效，并会合并进 policies：

opencode.jsonc
{
  "experimental": {
    "policies": [{ "action": "provider.use", "resource": "openai", "effect": "deny" }],
  },
}

语句

每条语句有三个字段：

字段取值含义
actionprovider.use、tool.use、integration.connect、integration.use、mcp.use、skill.use、plugin.use、websearch.use被控制的操作
resource字符串或通配符模式语句适用的对象；取决于 action
effectallow、deny语句命中时的决定

校验失败的语句会被丢弃，并在服务器日志里给出警告；列表里其余语句仍然生效。编辑 deny 之后记得查看日志。

匹配

资源使用与权限相同的整值通配符：* 匹配零个或多个字符，? 匹配一个。

opencode.jsonc
{
  "policies": [{ "action": "provider.use", "resource": "company-*", "effect": "deny" }],
}

这会禁用 company-us 和 company-eu。以 * 结尾的模式还匹配不带参数的值本身，所以 shell:git push * 同时覆盖单独的 git push。

顺序

多条语句同时命中时，最后一条胜出。没有「越具体越优先」的规则，所以把宽泛的语句放前面、例外放后面。什么都没命中时，动作默认允许。

opencode.jsonc
{
  "policies": [
    { "action": "provider.use", "resource": "*", "effect": "deny" },
    { "action": "provider.use", "resource": "anthropic", "effect": "allow" },
  ],
}

这样只有 Anthropic 可用。

提供商

provider.use 控制一个提供商是否可用。资源是提供商 ID：anthropic、openai、opencode，或 Providers里定义的自定义 ID：

opencode.jsonc
{
  "providers": {
    "company-ai": {
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": { "baseURL": "https://ai.company.example/v1" },
    },
  },
  "policies": [
    { "action": "provider.use", "resource": "*", "effect": "deny" },
    { "action": "provider.use", "resource": "company-ai", "effect": "allow" },
  ],
}

providers 条目负责配置端点；策略语句则让它成为 OpenCode 唯一会用的提供商。无论提供商从哪条途径被引入——目录数据、环境变量、已保存的账号、内置插件或配置文件——策略都会生效。

请用 provider.use 取代 V1 的 enabled_providers 和 disabled_providers 列表。V1 文件仍然能加载；见 从 V1 迁移。

工具

tool.use 语句对权限检查做硬性拒绝。资源是 <action>:<value>，与工具检查的每个资源进行匹配：

opencode.jsonc
{
  "policies": [
    { "action": "tool.use", "resource": "shell:git push *", "effect": "deny" },
    { "action": "tool.use", "resource": "edit:*.env", "effect": "deny" },
    { "action": "tool.use", "resource": "webfetch:*", "effect": "deny" },
  ],
}

被拒绝的检查直接以 Blocked by configuration policy 失败，而不是弹窗询问。它在智能体规则和保存的批准之后生效，所以既能压过 ask，也能压过「总是允许（Allow always）」的批准。

模式拦截内容
shell:*所有 shell 命令
read:*/.ssh/*读取 SSH 相关材料
external_directory:*任何超出 Location 或 worktree 的访问
subagent:general启动某个子智能体
github_delete_repository:*某个 MCP 工具
*所有尚未被拒绝的动作

tool.use 的 allow 永远不会授予访问权限，它只是解除更早的一条更宽的 deny，之后仍由智能体自己的规则说了算：

opencode.jsonc
{
  "policies": [
    { "action": "tool.use", "resource": "shell:*", "effect": "deny" },
    { "action": "tool.use", "resource": "shell:git status *", "effect": "allow" },
  ],
}

这样 git status 会回落到智能体的 shell 权限规则；其它所有命令都被拦截。

⚠️ 注意

策略只能「收紧」不能「放宽」：tool.use 的 allow 只是解除前面的 deny，真正的访问与否仍由权限规则决定。别指望写一条 policy allow 就能绕过权限的 ask——那是两套体系。

集成

集成（integration）指你在 /connect 里连接的任何东西：OpenCode Console（opencode）、某个提供商（如 anthropic）、某个网页搜索服务（如 exa），或知名的配置来源（如 https://ai.acme.com）。登录 MCP 服务器不受集成策略影响；要控制 MCP 服务器请用 mcp.use。

integration.connect 控制 /connect 列出哪些集成、哪些可以连接。资源是集成 ID。

integration.use 控制一个集成提供的一切：它的提供商和模型、它的网页搜索，以及 Console 工作区或知名来源下发的 MCP 服务器和配置。资源是 <integration>#<account>，account 是连接的组织或账号 ID，如 opencode#org_01M3CAP8H43Z49CER6NT0Y3ZF1。没有连接账号时，资源就是裸的集成 ID：未登录的免费版是 opencode，环境变量里有 ANTHROPIC_API_KEY 是 anthropic，opencode.json 里的提供商则是其提供商 ID。

下面这条 MDM 策略要求「只用一个 Console 工作区，其它一概不要」：

opencode.jsonc
{
  "policies": [
    { "action": "integration.connect", "resource": "*", "effect": "deny" },
    { "action": "integration.connect", "resource": "opencode", "effect": "allow" },
    { "action": "integration.use", "resource": "*", "effect": "deny" },
    { "action": "integration.use", "resource": "opencode#org_01M3CAP8H43Z49CER6NT0Y3ZF1", "effect": "allow" },
  ],
}

这样 /connect 只提供 Console 让成员登录。免费版、个人 Console 账号、其它组织、环境变量里的 API key、opencode.json 里的提供商——全部不可用。工作区的提供商、MCP 服务器和网页搜索正常工作，在 Console 里改动它们也不需要发新的 MDM 配置文件。

只有托管策略（managed policies）可以扣留集成下发的 MCP 服务器和配置；无论哪种情况，集成自身的策略都继续适用。

MCP、技能与插件

动作资源
mcp.useMCP 服务器，按其配置名称
skill.use技能，按其 ID
plugin.use插件，按不带版本号的包名或绝对路径
opencode.jsonc
{
  "policies": [
    { "action": "mcp.use", "resource": "*", "effect": "deny" },
    { "action": "mcp.use", "resource": "github", "effect": "allow" },
    { "action": "plugin.use", "resource": "opencode-acme-cli", "effect": "deny" },
  ],
}

被禁用的 MCP 服务器或技能会被移除，被禁用的插件不会被加载——无论它是怎么配置进来的。

从 integration.use 升级

在 OpenCode 2.2.3 之前，integration.use 通过 mcp:、skill:、plugin: 前缀覆盖 MCP 服务器、技能和插件。带前缀的语句仍然加载，并被转换成 mcp.use、skill.use 或 plugin.use。

没有这些前缀的语句（包括裸 *）现在改指集成。像这样一条宽泛的 deny：

opencode.jsonc
{ "action": "integration.use", "resource": "*", "effect": "deny" }

不再拦截 MCP 服务器、技能或插件。它会拦截所有提供商（包括免费版），除非后面的语句 allow 某个集成。想保留旧含义，把它换成：

opencode.jsonc
{
  "policies": [
    { "action": "mcp.use", "resource": "*", "effect": "deny" },
    { "action": "skill.use", "resource": "*", "effect": "deny" },
    { "action": "plugin.use", "resource": "*", "effect": "deny" },
  ],
}

例外同样照此迁移：integration.use 的 mcp:github 变成 mcp.use 的 github；skill:team:review 变成 skill.use 的 team:review。

低于 2.2.3 的客户端会忽略 integration.connect、integration.use（新含义）、mcp.use、skill.use 和 plugin.use，所以凡是依赖它们的场合，都要求 2.2.3 或更新版本。

网页搜索

websearch.use 控制 websearch 工具可以使用哪些网页搜索提供商。资源是提供商 ID：Console 提供的 OpenCode Web Search 是 opencode，内置提供商如 exa、firecrawl、parallel、tavily、tinyfish，或插件添加的提供商 ID。

opencode.jsonc
{
  "policies": [
    { "action": "websearch.use", "resource": "*", "effect": "deny" },
    { "action": "websearch.use", "resource": "opencode", "effect": "allow" },
  ],
}

被禁用的搜索提供商会移除，即使它们不需要 API key 也能工作（如 Exa 和 TinyFish）。当所有提供商都被禁用时，websearch 工具不再被提供。低于 2.2.6 的客户端会忽略 websearch.use。

优先级

普通设置让「离得最近的配置」胜出。策略正好相反：来自更宽范围配置的语句更晚求值，因此会覆盖更窄的。托管配置和已连接的 Console 永远压过用户和项目文件。

权威级别来源
1（最高）macOS 托管偏好（/Library/Managed Preferences/ai.opencode.managed.plist）
2系统级 opencode.json(c)（/Library/Application Support/opencode、/etc/opencode、%ProgramData%\opencode）
3已连接的 OpenCode Console 工作区
4全局 ~/.config/opencode/opencode.json(c)
5直接的 opencode.json(c)；外层目录压过内层
6（最低）.opencode/opencode.json(c)；外层目录压过内层

仓库无法重新启用你全局禁用的提供商：

~/.config/opencode/opencode.jsonc
{
  "policies": [{ "action": "provider.use", "resource": "openai", "effect": "deny" }],
}
project/opencode.jsonc无效的尝试
{
  "policies": [{ "action": "provider.use", "resource": "openai", "effect": "allow" }],
}

openai 仍然被禁。同一个文件里，语句保持书写顺序。

💡 扩展

「宽的语句更晚求值、因此胜出」这个设计正反着用正好：日常规则写在项目文件里（窄），组织红线写进托管配置或 Console（宽）——红线永远压过项目里的「小聪明」。这也是为什么优先级表从「越机器托管」到「越靠近仓库」排列。

Console

OpenCode Console 上的工作区会把它的 Providers 和 Tools 策略编译成常规的 policies 语句放进工作区配置。OpenCode 合并这份配置时，把它当成一个排在托管偏好和系统文件之下、其余配置之上的配置文件：组织的 deny 无法被仓库或用户的 allow 解除；组织的 allow 则能解除更低权威的 deny。托管偏好和系统文件仍然压过工作区。

这些语句产生的拒绝会点名工作区：

text
Blocked by Acme's policy

语句跟随已连接的账号：

事件结果
Console 策略变更在下次拉取时生效，约每分钟一次
切换到另一个工作区语句替换为该工作区的语句
断开连接语句清空
Console 不可达该连接的最近语句继续生效

Console 插件和策略插件无法在 plugins 里禁用；见插件的控制一节。

⚠️ 注意

策略不配置端点或凭证，也无法让一个本来就不可用的提供商变得可用。它也不给插件代码做沙箱隔离：被禁用的提供商是在正常的提供商与模型路径上被拦下来的。
