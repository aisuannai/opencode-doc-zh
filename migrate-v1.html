从 V1 迁移

OpenCode 1 和 OpenCode 2 都用 opencode 命令，默认不再并排安装。装 V2 前先卸掉包管理器装的 V1；V2 的 curl 安装器会直接替换 V1 的二进制。

破坏性变更

V2 有三处有意的破坏性变更：

  • 插件迁移：插件使用新的插件 API。
  • 服务器 API 与客户端：全新契约。
  • 终端客户端配置：从分层的 tui.json(c) 文件迁移到一个全局的 cli.json（自动迁移）。

上述范围之外、V1 里受支持的功能，目标是保持与 V1 兼容。V1 schema 接受的某些字段从未有过 V2 等价物，会被有意忽略；它们列在「接受但不受支持的字段」一节。

既有受支持的服务器配置字段、智能体定义、命令定义、技能以及 .opencode/ 里的其它文件，应当无需改动即可继续工作。如果本指南描述的受支持行为在 V2 里不工作了，请把它当作兼容性 bug，而不是预期的迁移要求。

⚠️ 注意

如果受支持的 V1 功能在 V2 里失效，按 故障排查的指引提交一个兼容性 issue。

安装 V2

按安装说明安装 V2 终端客户端。

不需要先把一切都改写好再启动 V2。务实的迁移步骤是：

  1. 保留既有的配置和基于文件的定义。
  2. 启动 V2，验证模型、凭证、智能体、权限和 MCP 服务器。
  3. 迁移插件——V1 的插件实现无法在 V2 里运行。
  4. 迁移调用服务器 API 的集成。
  5. 准备好了再把配置转换成 V2 原生形态。这一步是可选的。

在验证迁移期间，保留一份 V1 设置的备份。V1 和 V2 使用相同的配置位置，所以配置一旦被转换成 V2 专属形态，就不要再让 V1 指向它们。

配置

本节同时覆盖 JSON/JSONC 配置和 .opencode/ 下基于文件的定义。

直接用现有配置

V2 从与 V1 相同的位置读取既有的系统级、全局和项目配置：

text
/Library/Application Support/opencode/opencode.json(c)
/etc/opencode/opencode.json(c)
%ProgramData%\opencode\opencode.json(c)
/Library/Managed Preferences/<user>/ai.opencode.managed.plist
/Library/Managed Preferences/ai.opencode.managed.plist
~/.config/opencode/opencode.json(c)
<project>/opencode.json(c)
<project>/.opencode/opencode.json(c)

V2 在内存里把受支持的 V1 字段和 V2 原生字段规范化，不改写源文件。既有受支持的 V1 配置的目标就是继续可用，所以试用或采用 V2 不需要先转换它。

与 V1 一样，系统配置和 macOS 托管偏好优先级最高，它们的设置覆盖全局和项目文件。它们的策略（包括迁移来的 enabled_providers 和 disabled_providers）同样压过全局和项目策略。覆盖某个设置拦不住用户添加提供商、MCP 服务器、智能体或插件，所以管理员强制的限制要用 policies 表达，而不是 permissions 这类普通设置。

让 OpenCode 替你迁移

V1 配置格式继续受支持。V2 原生格式是可选的，它让若干设置更明确、更顺手。

推荐的迁移路径是让 OpenCode 替你更新配置：

text
Migrate my OpenCode configuration, including file-based definitions, from the V1 format to the native V2 format.
Preserve its behavior and all unrelated settings.

OpenCode 可以检查完整文件、应用下述相关变更，并避免重写无需变动的设置。转换不必一次完成：受支持的 V1 字段和 V2 原生字段可以在顶层共存。两种形式设置了同一个规范值时，无论 JSON 键顺序如何，有效的 V2 原生值优先。

嵌套混用是有意受限的。OpenCode 能识别 mcp、compaction、experimental 内的 V1/V2 混合成员，但不会在单个智能体、提供商、命令或模型内部递归推断格式。这些嵌套条目请整体保持一种格式。受支持的 V1 语法本身是安静的；畸形值、不受支持的旧字段和冲突的 V1/V2 值会产生警告，同时其它有效设置继续加载。

权限与工具

V1 按工具分组权限效果。V2 用一个有序的 permissions 数组，优先级和例外一目了然：

jsoncV1 → V2
// V1
{
  "permission": {
    "bash": {
      "git push *": "ask"
    },
    "edit": "allow"
  },
  "tools": {
    "websearch": false
  }
}

// V2
{
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "edit", "resource": "*", "effect": "allow" },
    { "action": "websearch", "resource": "*", "effect": "deny" }
  ]
}

权限动作也改名了：bash 变为 shell，task 变为 subagent，write 和 patch 变为 edit。V2 的有序规则格式见 权限一章。

V2 里待办清单（Todos）默认关闭。想开启用实验性开关；它可能在未来的版本中变化或被移除，见 配置的实验性设置一节：

opencode.jsonc
{
  "experimental": {
    "todo": true,
  },
}

⚠️ 注意

V1 访问项目之外的路径前会先询问；V2 不会：external_directory 默认允许。想保留 V1 行为，在 permissions 里加 { "action": "external_directory", "resource": "*", "effect": "ask" }。这是安全行为变更，迁移时务必检查。

智能体与模式

单数的 agent 和已弃用的 mode 映射统一为 agents。智能体字段也更贴合 V2 配置的其余部分：

jsoncV1 → V2
// V1
{
  "agent": {
    "reviewer": {
      "prompt": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-5-5",
      "variant": "high",
      "disable": false,
      "permission": {
        "edit": "deny"
      }
    }
  }
}

// V2
{
  "agents": {
    "reviewer": {
      "system": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-5-5#high",
      "disabled": false,
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}

prompt 变为 system，disable 变为 disabled，单独的 variant 在模型引用后面拼上 #。maxSteps 变为 steps。旧 mode 映射里的条目变成主智能体。

智能体的 request.body 会被保留但不会发送给模型，所以 V1 的 temperature、top_p 和 options 在那里没有效果。请改设在模型变体上。DeepSeek 只在关闭思考（thinking off）时应用 temperature，所以这个变体连思考也一起关掉：

opencode.jsonc
{
  "providers": {
    "opencode": {
      "models": {
        "deepseek-v4.1-flash": {
          "variants": [{ "id": "review", "body": { "thinking": { "type": "disabled" }, "temperature": 0.2 } }],
        },
      },
    },
  },
  "agents": {
    "reviewer": { "model": "opencode/deepseek-v4.1-flash#review" },
  },
}

提供商 JSON 字段用 body，提供商包选项用 settings。见 模型的选项一节。

快照

把单数的 snapshot 字段改名为 snapshots，布尔值不变：

jsoncV1 → V2
// V1
{ "snapshot": false }

// V2
{ "snapshots": false }

媒体

把单数的 attachment 对象改名为 media，嵌套的图片设置名称不变：

jsoncV1 → V2
// V1
{ "attachment": { "image": { "auto_resize": true } } }

// V2
{ "media": { "image": { "auto_resize": true } } }

MCP 服务器

V2 把服务器收进 mcp.servers，用反向的 disabled 替换 enabled，并把超时按用途拆分：

jsoncV1 → V2
// V1
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "@playwright/mcp"],
      "enabled": true,
      "timeout": 30000
    }
  }
}

// V2
{
  "mcp": {
    "servers": {
      "playwright": {
        "type": "local",
        "command": ["npx", "@playwright/mcp"],
        "disabled": false,
        "timeout": {
          "catalog": 30000,
          "execution": 30000
        }
      }
    }
  }
}

远程 OAuth 字段改用 snake case：clientId 变为 client_id，clientSecret 变为 client_secret，callbackPort 变为 callback_port，redirectUri 变为 redirect_uri。V1 的 experimental.mcp_timeout 也会变成默认的 mcp.timeout.catalog 和 mcp.timeout.execution。见 MCP 服务器。

上下文压缩

V2 把保留上下文的 token 预算收进 keep，给预留量起了更清晰的名字：

jsoncV1 → V2
// V1
{
  "compaction": {
    "preserve_recent_tokens": 8000,
    "reserved": 20000
  }
}

// V2
{
  "compaction": {
    "keep": {
      "tokens": 8000
    },
    "buffer": 20000
  }
}

V1 的 token 数原样沿用。V2 还接受模型窗口的百分比，如 "buffer": "15%"，适合窗口大小不同的模型。

auto 保持原名。V2 没有原生的 tail_turns 或 prune 字段，这两个遗留字段会被忽略并警告。近期上下文改为按 token 预算保留。见 上下文压缩。

技能

V1 把额外的技能路径和 URL 分开。V2 把两者合并为一个有序数组：

jsoncV1 → V2
// V1
{
  "skills": {
    "paths": ["./team-skills"],
    "urls": ["https://example.com/skills/"]
  }
}

// V2
{
  "skills": ["./team-skills", "https://example.com/skills/"]
}

既有的技能文件和 .opencode/skills/ 的自动发现不变。见 Skills。

命令

把单数的 command 映射改名为 commands，subtask 改为 subagent。单独的模型 variant 拼进模型引用：

jsoncV1 → V2
// V1
{
  "command": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-5-5",
      "variant": "high",
      "subtask": true
    }
  }
}

// V2
{
  "commands": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-5-5#high",
      "subagent": true
    }
  }
}

template、description 和 agent 名称不变。遗留的 subtask 仍然接受；被委派的命令现在会自动在后台运行并向父会话汇报结果。既有 Markdown 命令定义继续支持。见 自定义命令。

References

把已弃用的单数 reference 映射改名为 references：

jsoncV1 → V2
// V1
{ "reference": { "docs": "../docs" } }

// V2
{ "references": { "docs": "../docs" } }

V1 其实已经接受 references，所以文件里用它的话无需改动。引用条目的形态保持不变。见 References。

提供商

把单数的 provider 映射改名为 providers。V2 把运行时包、端点和请求设置分开：

jsoncV1 → V2
// V1
{
  "provider": {
    "acme": {
      "npm": "@ai-sdk/openai-compatible",
      "api": "https://llm.example.com/v1",
      "options": {
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}

// V2
{
  "providers": {
    "acme": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": {
        "baseURL": "https://llm.example.com/v1",
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}

V1 的 npm 变为 package，AI SDK 包加 aisdk: 前缀。api 变为 settings.baseURL。提供商的 options 按请求角色拆分为 settings、headers 和 body。options.setCacheKey 变为提供商上的 compatibility.supportsPromptCacheKey。见 Providers。

V2 合并了两个遗留的提供商命名空间：

V1 提供商 IDV2 规范提供商 ID
azure-cognitive-servicesazure
google-vertex-anthropicgoogle-vertex

不含糊的 V1 提供商、智能体、命令和提供商过滤字段，迁移时使用这些规范 ID。共享的顶层 model 字段保留其原样提供商 ID（因为同一语法在 V2 原生配置里也有效）；迁移遗留内置提供商时，把该字段更新为规范 ID。

模型与变体

模型仍然嵌套在提供商之下，但若干模型字段变得更明确：

  • id 变为 modelID。
  • tool_call 和 modalities 变为 capabilities.tools、capabilities.input 和 capabilities.output。
  • status 为 "deprecated" 的变为 disabled: true。
  • 缓存成本从 cache_read 和 cache_write 移到 cache.read 和 cache.write。
  • 提供商专属的 options 变为 settings。
  • V1 的 variants 对象变成 V2 的数组，每个条目带 id。
jsoncV1 → V2
// V1
{
  "variants": {
    "high": {
      "reasoningEffort": "high"
    }
  }
}

// V2
{
  "variants": [
    {
      "id": "high",
      "settings": {
        "reasoningEffort": "high"
      }
    }
  ]
}

完整的 V2 原生模型形态见 模型。

没有直接原生等价物的受支持字段

大多数保持同样形态的字段——包括 shell、model、default_agent、watcher、formatter、instructions、enterprise 和 tool_output——无需迁移。

V2 接受并保留 lsp 配置，但不运行语言服务器、不暴露 LSP 工具、也不产生 LSP 诊断。依赖这些能力的工作流，请改用项目的 lint、typecheck 或编译器命令。

V1 的提供商过滤器没有一一对应的 V2 原生配置字段，但其行为仍通过策略支持：

  • enabled_providers 变成内部「默认全部 deny」的提供商策略，再对列出的提供商 allow。
  • disabled_providers 变成对所列提供商的内部 deny 策略。
  • autoupdate 变成 update：false 映射为 "disable"，"notify" 映射为 "notify"，true 映射为 "auto"。
  • small_model 变成内置 title 智能体的 model 选择。V2 原生配置应改用 agents.title.model。

这些字段可以继续用 V1 语法。OpenCode 会静默规范化它们，不产生警告。

接受但不受支持的字段

V1 schema 还接受一些没有 V2 受支持行为的字段。V2 忽略这些值并发警告，避免它们被误当作生效的配置：

  • logLevel：启动 OpenCode 时用 OPENCODE_LOG_LEVEL。
  • server：使用 V2 的服务和显式服务器选项；服务器 API 是有意的破坏性变更。
  • 顶层 subagent_depth：改用 experimental.subagent_depth。
  • compaction.tail_turns 和 compaction.prune：V2 改用 compaction.keep.tokens 和基于检查点的压缩。
  • V1 JSON 配置里的智能体 name。
  • 没有 type 的「仅 enabled」V1 MCP 条目。
  • V1 实验性字段 batch_tool、openTelemetry、primary_tools、continue_loop_on_deny。
  • V1 提供商字段 id、whitelist、blacklist。
  • V1 提供商-模型字段 release_date、attachment、reasoning、temperature、experimental、非 deprecated 的 status，以及布尔值 interleaved。

忽略这些字段是有意的，不算兼容性倒退。如果 V2 没有保留本指南标明受支持的行为，按 故障排查的指引反馈。

智能体文件

V1 智能体文件可用 agent/、agents/、mode/ 或 modes/。V2 仍然发现这四个目录。V2 首选的位置是：

text
.opencode/agents/<name>.md

V1 的 mode/ 或 modes/ 目录下的文件代表主智能体。把它们挪进 agents/ 时，在 frontmatter 里加上 mode: primary。agent/ 下的文件可以直接挪到 agents/，路径推导出的 ID 不变。

把 frontmatter 转换成 V2 原生字段时：

  • Markdown 正文继续作为智能体的系统指令。
  • prompt 在 JSON 配置里改名为 system；文件正文不需要 system 字段。
  • disable 改为 disabled，permission 改为 permissions。
  • model 与 variant 合并为 provider/model#variant。
  • 采样与提供商选项设在模型变体上，如上文所示。

V1 智能体 frontmatter 已弃用，但会被自动翻译。每个文件按一种格式读取。使用了 permissions、request、system 或 disabled 任一字段的文件按 V2 读取，其中出现的 V1 字段（如 name、tools、permission、temperature）会被忽略并记录警告。使用 V1 字段的其它文件按 V1 读取。一个文件的 frontmatter 要么整体转换，不要混用两种格式。见 Agents。

命令文件

V1 命令文件可用 command/ 或 commands/。V2 两者都发现。首选位置是：

text
.opencode/commands/<name>.md

把文件从 command/ 挪到 commands/ 下相同的相对路径，即可保留命令名。Markdown 正文仍是命令模板，frontmatter 的 description 和 agent 名称不变。把 subtask 改名为 subagent 即可使用后台委派的原生名称。frontmatter 里如果有分开的 model 和 variant 字段，把变体拼到模型后面并删掉 variant：

yamlV1 → V2
# V1
model: anthropic/claude-sonnet-5-5
variant: high
subtask: true

# V2
model: anthropic/claude-sonnet-5-5#high
subagent: true

见 自定义命令。

技能文件

V2 从 .opencode/skill/ 和 .opencode/skills/ 两处发现技能。首选布局是：

text
.opencode/skills/<skill-id>/SKILL.md

移动时带上整个技能目录，而不只是 SKILL.md，这样相对脚本、引用和其它配套文件才能继续可用。目录名保持不变以保留技能 ID。既有技能的 frontmatter 和 Markdown 正文不需要 V2 重写。见 Skills。

指令文件

既有的 AGENTS.md 原地保留。V2 发现全局的 ~/.config/opencode/AGENTS.md，以及从当前目录向上到家目录的环境内 AGENTS.md；家目录之外的项目在项目根停止。

V2 保留 V1 的 CLAUDE.md 回退：没有 AGENTS.md 的目录用它的 CLAUDE.md，缺失全局 AGENTS.md 时由 ~/.claude/CLAUDE.md 顶替。OPENCODE_DISABLE_CLAUDE_CODE 跳过所有 CLAUDE.md，OPENCODE_DISABLE_CLAUDE_CODE_PROMPT 也一样（它在 V1 里只跳过 ~/.claude/CLAUDE.md）。与 V1「沿目录树向上找到第一个文件名就停」不同，V2 按目录逐个挑选，所以根目录的 AGENTS.md 不再遮蔽嵌套的 CLAUDE.md。见 指令文件。

终端客户端配置

V2 用一个全局的终端客户端配置文件取代分层的 V1 tui.json(c) 文件：

text
~/.config/opencode/cli.json

这个文件由终端客户端管理；后台服务不加载它。cli.json 不存在时，第一次 V2 终端客户端启动会把受支持的全局 tui.json 设置和持久化偏好自动迁移，同时不改动 V1 的文件。项目级客户端配置不迁移，因为 V2 的客户端配置是全局的。当前的客户端设置参考见 TUI 设置。

插件

把 plugin 改名为 plugins。「包 + 选项」的元组换成对象：

jsoncV1 → V2
// V1
{
  "plugin": ["opencode-example-plugin", ["./plugin/local.ts", { "enabled": true }]]
}

// V2
{
  "plugins": [
    "opencode-example-plugin",
    {
      "package": "./plugin/local",
      "options": { "enabled": true }
    }
  ]
}

V2 从 .opencode/plugin/ 和 .opencode/plugins/ 两处发现本地插件；V2 文件请用 .opencode/plugins/。配置的本地路径必须是目录，所以迁移后的插件要挪到 ./plugin/local/index.ts。

⚠️ 注意

V1 的插件实现无法在 V2 里运行。挪文件、改配置条目名都不够——必须按新的插件 API 重写。入口、钩子、工具、事件和包导出的迁移，见专门的插件迁移指南。

服务器 API 与客户端

OpenCode 2 有修订过的、更顺手的服务器 API 和一套新客户端。调用 V1 服务器 API 的集成必须迁移到 V2 API。

用 @opencode/client 包访问已发布的 V2 API。其端点、请求类型和响应见生成的 API 参考。

服务器认证

V2 服务器仍然使用 HTTP Basic 认证，但有这些变化：

  • OPENCODE_PASSWORD 设置密码。OPENCODE_SERVER_PASSWORD 仍然有效。
  • 不再支持 OPENCODE_SERVER_USERNAME。用户名固定为 opencode。
bashV1 → V2
# V1
OPENCODE_SERVER_USERNAME=alice OPENCODE_SERVER_PASSWORD=secret opencode serve

# V2
OPENCODE_PASSWORD=secret opencode serve

见 Web 界面的认证一节。

验证你的设置

把 V2 用于日常工作之前，先在一个项目里验证模型、提供商凭证、智能体、权限、MCP 服务器和插件。确认你需要的 V2 行为之前，保留 V1 环境；并且不要让 V1 指向已经转换成 V2 原生形态的配置。

💡 扩展

给拖延症的迁移清单：V2 对绝大多数 V1 配置是「直接能跑」的，真正的迁移工作量集中在两处——插件（必须重写）和调用服务器 API 的集成。如果你只是用 TUI 加一点 JSON 配置，多半五分钟就能迁完；如果有一堆自定义插件，预留一个下午。拿不准时先复制一份 ~/.config/opencode/ 和各项目的 .opencode/，随时可以回退。
